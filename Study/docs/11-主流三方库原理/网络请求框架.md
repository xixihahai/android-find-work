# 网络请求框架

## 速记总结

> **一句话理解**：OkHttp 是"高效的邮递系统"——拦截器链像流水线逐站处理信件，连接池像重复利用邮路；Retrofit 是"自动填表机"——你只需声明要寄什么，动态代理帮你把注解翻译成完整的请求。

### 核心概念速记表

| 组件 | 一句话记忆 | 生活类比 |
|------|-----------|---------|
| OkHttpClient | 整个网络请求的配置中心 | 邮局总部，配置所有邮递规则 |
| Interceptor | 请求/响应的拦截处理器 | 流水线上的质检工人，逐个检查加工 |
| Dispatcher | 异步请求的调度器 | 邮局调度员，决定同时派多少邮递员 |
| ConnectionPool | TCP 连接复用池 | 常用邮路不拆，下次直接走 |
| Retrofit | 声明式 API 接口转换器 | 自动填表窗口，你说要什么它帮你填请求单 |
| ServiceMethod | 注解解析后的方法描述 | 填好的表单模板，缓存起来下次直接用 |
| Converter | 请求/响应数据格式转换 | 翻译官，把中文翻译成英文再翻回来 |
| CallAdapter | 返回类型适配器 | 取件方式选择——自取、快递柜、送货上门 |

```
│    • 添加 User-Agent                                                     │

                       │ chain.proceed(networkRequest)
                       ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  ③ CacheInterceptor（缓存）                                              │
│  ─────────────────────────────────────────────────                       │
│  职责：                                                                  │
│    • 根据 CacheStrategy 决定用【缓存】还是【网络】                       │
│    • networkRequest==null && cacheResponse==null → 返回 504              │
│    • networkRequest==null → 直接返回缓存                                 │
│    • 发起网络请求 → 304 Not Modified → 更新缓存头后返回缓存body           │

┌──────────────────────────────────────────────────────────────────────────┐
│  ④ ConnectInterceptor（建立连接）                                        │
│  ─────────────────────────────────────────────────                       │
│  职责：                                                                  │
│    • 从 ConnectionPool 找可复用连接（相同 Address + Route）               │
│    • 没有可复用 → 创建新的 RealConnection → TCP 握手                      │
│    • 如果是 HTTPS → TLS 握手                                             │
│    • 如果是 HTTP/2 → ALPN 协商                                           │
│    • 找到/创建连接后 → 创建 Exchange（编解码器）                          │
│  要点：                                                                  │
│    • 连接池默认：maxIdleConnections=5, keepAliveDuration=5min            │

│    • 如果有请求体 → 写入请求体（Expect: 100-continue 处理）               │
│    • 刷新缓冲区（flush）                                                 │
│    • 读取响应头 → 构建 Response                                          │

│  要点：                                                                  │
│    • 这是拦截器链的【最后一环】，不再调用 chain.proceed()                 │
│    • 使用 Okio 的 Sink/Source 进行高效 I/O                               │
│    • 大文件上传时，先发 100-continue 探测服务器是否接受                   │
```

### 2.4 拦截器链

```java
// RealCall.java
@Override
public Response execute() throws IOException {
    synchronized (this) {
        if (executed) throw new IllegalStateException("Already Executed");
        executed = true;
    }
    try {
        client.dispatcher().executed(this);
        return getResponseWithInterceptorChain();
    } finally {
        client.dispatcher().finished(this);
    }
}

Response getResponseWithInterceptorChain() throws IOException {
    List<Interceptor> interceptors = new ArrayList<>();
    
    // 用户自定义拦截器
    interceptors.addAll(client.interceptors());
    
    // 内置拦截器
    interceptors.add(new RetryAndFollowUpInterceptor(client));
    interceptors.add(new BridgeInterceptor(client.cookieJar()));
    interceptors.add(new CacheInterceptor(client.cache()));
    interceptors.add(new ConnectInterceptor(client));
    
    if (!forWebSocket) {
        interceptors.addAll(client.networkInterceptors());
    }
    
    interceptors.add(new CallServerInterceptor(forWebSocket));
    
    // 创建拦截器链
    Interceptor.Chain chain = new RealInterceptorChain(interceptors, transmitter,
            null, 0, originalRequest, this, client.connectTimeoutMillis(),
            client.readTimeoutMillis(), client.writeTimeoutMillis());
    
    return chain.proceed(originalRequest);
}

// RealInterceptorChain.java
@Override
public Response proceed(Request request) throws IOException {
    // 调用下一个拦截器
    RealInterceptorChain next = new RealInterceptorChain(interceptors, transmitter,
            exchange, index + 1, request, call, connectTimeout, readTimeout, writeTimeout);
    Interceptor interceptor = interceptors.get(index);
    Response response = interceptor.intercept(next);
    return response;
}
```

### 2.3 连接池

```java
// ConnectionPool.java
public final class ConnectionPool {
    // 最大空闲连接数
    private final int maxIdleConnections;
    // 空闲连接存活时间
    private final long keepAliveDurationNs;
    // 连接队列
    private final Deque<RealConnection> connections = new ArrayDeque<>();
    
    // 获取连接
    @Nullable RealConnection get(Address address, StreamAllocation streamAllocation,
            Route route) {
        for (RealConnection connection : connections) {
            if (connection.isEligible(address, route)) {
                streamAllocation.acquire(connection, true);
                return connection;
            }
        }
        return null;
    }
    
    // 放回连接
    void put(RealConnection connection) {
        connections.add(connection);
        cleanupRunning = true;
        executor.execute(cleanupRunnable);
    }
    
    // 清理空闲连接
    long cleanup(long now) {
        // 遍历连接，清理空闲超时的连接
        for (Iterator<RealConnection> i = connections.iterator(); i.hasNext(); ) {
            RealConnection connection = i.next();
            if (connection.idleAtNanos + keepAliveDurationNs < now) {
                i.remove();
                connection.socket().close();
            }
        }
        return keepAliveDurationNs;
    }
}
```

```java
// Retrofit.java
public <T> T create(final Class<T> service) {
    // 验证接口
    validateServiceInterface(service);
    
    // 动态代理
    return (T) Proxy.newProxyInstance(
            service.getClassLoader(),
            new Class<?>[] { service },
            new InvocationHandler() {
                @Override
                public Object invoke(Object proxy, Method method, Object[] args)
                        throws Throwable {
                    // Object 方法直接调用
                    if (method.getDeclaringClass() == Object.class) {
                        return method.invoke(this, args);
                    }
                    
                    // 加载 ServiceMethod
                    return loadServiceMethod(method).invoke(args);
                }
            });
}

// 加载 ServiceMethod
ServiceMethod<?> loadServiceMethod(Method method) {
    ServiceMethod<?> result = serviceMethodCache.get(method);
    if (result != null) return result;
    
    synchronized (serviceMethodCache) {
        result = serviceMethodCache.get(method);
        if (result == null) {
            // 解析方法注解，创建 ServiceMethod
            result = ServiceMethod.parseAnnotations(this, method);
            serviceMethodCache.put(method, result);
        }
    }
    return result;
}

// HttpServiceMethod.java
static <ResponseT, ReturnT> HttpServiceMethod<ResponseT, ReturnT> parseAnnotations(
        Retrofit retrofit, Method method, RequestFactory requestFactory) {
    
    // 获取 CallAdapter
    CallAdapter<ResponseT, ReturnT> callAdapter =
            createCallAdapter(retrofit, method, adapterType, annotations);
    
    // 获取 Converter
    Converter<ResponseBody, ResponseT> responseConverter =
            createResponseConverter(retrofit, method, responseType);
    
    // 创建 HttpServiceMethod
    return new CallAdapted<>(requestFactory, callFactory, responseConverter, callAdapter);
}

// 执行请求
@Override
final @Nullable ReturnT invoke(Object[] args) {
    Call<ResponseT> call = new OkHttpCall<>(requestFactory, args, callFactory, responseConverter);
    return adapt(call, args);
}
```

### 3.1 缓存拦截器

```java
// CacheInterceptor.java
@Override
public Response intercept(Chain chain) throws IOException {
    // 获取缓存响应
    Response cacheCandidate = cache != null
            ? cache.get(chain.request())
            : null;
    
    // 缓存策略
    CacheStrategy strategy = new CacheStrategy.Factory(now, chain.request(), cacheCandidate)
            .compute();
    Request networkRequest = strategy.networkRequest;
    Response cacheResponse = strategy.cacheResponse;
    
    // 只使用缓存
    if (networkRequest == null) {
        return cacheResponse.newBuilder()
                .cacheResponse(stripBody(cacheResponse))
                .build();
    }
    
    // 发起网络请求
    Response networkResponse = chain.proceed(networkRequest);
    
    // 304 Not Modified
    if (networkResponse.code() == HTTP_NOT_MODIFIED) {
        Response response = cacheResponse.newBuilder()
                .headers(combine(cacheResponse.headers(), networkResponse.headers()))
                .cacheResponse(stripBody(cacheResponse))
                .networkResponse(stripBody(networkResponse))
                .build();
        cache.update(cacheResponse, response);
        return response;
    }
    
    // 缓存响应
    if (cache != null && HttpHeaders.hasBody(networkResponse)
            && CacheStrategy.isCacheable(networkResponse, networkRequest)) {
        CacheRequest cacheRequest = cache.put(networkResponse);
        return cacheWritingResponse(cacheRequest, networkResponse);
    }
    
    return networkResponse;
}
```

### 4.1 场景案例

#### 场景1：统一添加 Token 的拦截器

**为什么用**：每个需要认证的请求都要带 Token，手动在每个请求里加 header 会导致大量重复代码，忘加就 401。

**使用依据**：OkHttp 拦截器的责任链模式天然适合"统一预处理"，类似 AOP 的切面编程思想——把横切关注点（认证）从业务代码中抽离。

```kotlin
class AuthInterceptor(
    private val tokenProvider: () -> String?
) : Interceptor {
    
    override fun intercept(chain: Interceptor.Chain): Response {
        val originalRequest = chain.request()
        
        // 不需要认证的接口直接放行
        if (originalRequest.header("No-Auth") != null) {
            return chain.proceed(
                originalRequest.newBuilder()
                    .removeHeader("No-Auth")
                    .build()
            )
        }
        
        val token = tokenProvider() ?: return chain.proceed(originalRequest)
        
        val authenticatedRequest = originalRequest.newBuilder()
            .header("Authorization", "Bearer $token")
            .build()
        
        val response = chain.proceed(authenticatedRequest)
        
        // Token 过期自动刷新
        if (response.code == 401) {
            response.close()
            val newToken = refreshToken() // 同步刷新 Token
            if (newToken != null) {
                val retryRequest = originalRequest.newBuilder()
                    .header("Authorization", "Bearer $newToken")
                    .build()
                return chain.proceed(retryRequest)
            }
        }
        
        return response
    }
    
    private fun refreshToken(): String? {
        // 同步请求刷新 Token，注意线程安全
        // 多个请求同时 401 时需要加锁避免重复刷新
        synchronized(this) {
            // 双重检查：可能别的线程已经刷新了
            val currentToken = tokenProvider()
            // ... 执行刷新逻辑
            return currentToken
        }
    }
}

// 使用
val client = OkHttpClient.Builder()
    .addInterceptor(AuthInterceptor { UserManager.token })
    .build()

// 不需要认证的接口
interface ApiService {
    @Headers("No-Auth: true")
    @POST("login")
    suspend fun login(@Body request: LoginRequest): LoginResponse
    
    @GET("users/me")
    suspend fun getProfile(): User  // 自动带 Token
}
```

#### 场景2：请求重试和超时配置

**为什么用**：移动网络环境不稳定（地铁、电梯），需要合理的超时和重试机制避免用户看到一片空白。

**使用依据**：
- 连接超时要短（10s），因为连不上就是连不上，等太久体验差
- 读超时可以长一些（30s），因为某些接口确实慢
- 写超时看业务（上传大文件需要更长）
- 重试要考虑幂等性——GET 安全，POST 需谨慎

```kotlin
// 自定义重试拦截器（比 OkHttp 内置的更灵活）
class RetryInterceptor(
    private val maxRetries: Int = 3,
    private val retryInterval: Long = 1000L // 毫秒
) : Interceptor {
    
    override fun intercept(chain: Interceptor.Chain): Response {
        val request = chain.request()
        var response: Response? = null
        var exception: IOException? = null
        
        for (attempt in 0..maxRetries) {
            try {
                // 关闭上一次的 response
                response?.close()
                response = chain.proceed(request)
                
                // 服务端错误才重试，客户端错误（4xx）不重试
                if (response.isSuccessful || response.code in 400..499) {
                    return response
                }
                
                // 5xx 服务端错误 → 重试
                if (attempt < maxRetries) {
                    response.close()
                    Thread.sleep(retryInterval * (attempt + 1)) // 线性退避
                }
            } catch (e: IOException) {
                exception = e
                if (attempt < maxRetries) {
                    Thread.sleep(retryInterval * (attempt + 1))
                }
            }
        }
        
        // 所有重试都失败
        return response ?: throw exception ?: IOException("Unknown error after $maxRetries retries")
    }
}

// 配置不同业务场景的超时
val normalClient = OkHttpClient.Builder()
    .connectTimeout(10, TimeUnit.SECONDS)
    .readTimeout(30, TimeUnit.SECONDS)
    .writeTimeout(30, TimeUnit.SECONDS)
    .addInterceptor(RetryInterceptor(maxRetries = 2))
    .build()

// 上传专用 Client（超时更长）
val uploadClient = normalClient.newBuilder()
    .writeTimeout(120, TimeUnit.SECONDS)
    .readTimeout(120, TimeUnit.SECONDS)
    .addInterceptor(RetryInterceptor(maxRetries = 0)) // 上传不重试
    .build()
```

#### 场景3：缓存策略配置——离线模式实现

**为什么用**：新闻、文章类 App 在无网络时也需要展示上次加载的内容，而不是直接报错。

**使用依据**：OkHttp 的 CacheInterceptor 遵循 HTTP 缓存语义，但很多服务端没有正确设置 Cache-Control 头。通过自定义拦截器强制缓存策略，可以在客户端实现离线模式而不依赖服务端配合。

```kotlin
// 离线模式缓存拦截器
class OfflineCacheInterceptor(
    private val context: Context
) : Interceptor {
    
    override fun intercept(chain: Interceptor.Chain): Response {
        var request = chain.request()
        
        if (!isNetworkAvailable(context)) {
            // 无网络 → 强制使用缓存，即使缓存已过期
            request = request.newBuilder()
                .cacheControl(CacheControl.FORCE_CACHE)
                .build()
        }
        
        return chain.proceed(request)
    }
    
    private fun isNetworkAvailable(context: Context): Boolean {
        val cm = context.getSystemService(Context.CONNECTIVITY_SERVICE) as ConnectivityManager
        val network = cm.activeNetwork ?: return false
        val capabilities = cm.getNetworkCapabilities(network) ?: return false
        return capabilities.hasCapability(NetworkCapabilities.NET_CAPABILITY_INTERNET)
    }
}

// 网络拦截器：强制服务端响应可缓存（服务端没设 Cache-Control 时）
class ForceCacheNetworkInterceptor : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val response = chain.proceed(chain.request())
        
        val cacheControl = CacheControl.Builder()
            .maxAge(5, TimeUnit.MINUTES) // 缓存有效期 5 分钟
            .build()
        
        return response.newBuilder()
            .removeHeader("Pragma")
            .removeHeader("Cache-Control")
            .header("Cache-Control", cacheControl.toString())
            .build()
    }
}

// 组合使用
val cacheDir = File(context.cacheDir, "http_cache")
val cache = Cache(cacheDir, 50L * 1024 * 1024) // 50MB

val client = OkHttpClient.Builder()
    .cache(cache)
    .addInterceptor(OfflineCacheInterceptor(context))          // 应用拦截器
    .addNetworkInterceptor(ForceCacheNetworkInterceptor())     // 网络拦截器
    .build()
```

#### 场景4：文件上传/下载进度监听

**为什么用**：用户上传头像、简历等文件时需要看到进度条，否则不知道是在传还是卡死了。

**使用依据**：OkHttp 的 RequestBody/ResponseBody 基于 Okio 的 Source/Sink 流式 API，通过自定义包装类就能在数据流经时统计进度，不需要把文件全部读入内存。

```kotlin
// 带进度监听的 RequestBody
class ProgressRequestBody(
    private val delegate: RequestBody,
    private val listener: (bytesWritten: Long, totalBytes: Long) -> Unit
) : RequestBody() {
    
    override fun contentType(): MediaType? = delegate.contentType()
    
    override fun contentLength(): Long = delegate.contentLength()
    
    override fun writeTo(sink: BufferedSink) {
        val totalBytes = contentLength()
        var bytesWritten = 0L
        
        // 包装 Sink，统计写入字节数
        val countingSink = object : ForwardingSink(sink) {
            override fun write(source: Buffer, byteCount: Long) {
                super.write(source, byteCount)
                bytesWritten += byteCount
                listener(bytesWritten, totalBytes)
            }
        }
        
        val bufferedSink = countingSink.buffer()
        delegate.writeTo(bufferedSink)
        bufferedSink.flush()
    }
}

// 带进度监听的 ResponseBody（下载）
class ProgressResponseBody(
    private val delegate: ResponseBody,
    private val listener: (bytesRead: Long, totalBytes: Long) -> Unit
) : ResponseBody() {
    
    override fun contentType(): MediaType? = delegate.contentType()
    override fun contentLength(): Long = delegate.contentLength()
    
    override fun source(): BufferedSource {
        val totalBytes = contentLength()
        var bytesRead = 0L
        
        val countingSource = object : ForwardingSource(delegate.source()) {
            override fun read(sink: Buffer, byteCount: Long): Long {
                val read = super.read(sink, byteCount)
                bytesRead += if (read != -1L) read else 0
                listener(bytesRead, totalBytes)
                return read
            }
        }
        
        return countingSource.buffer()
    }
}

// 使用示例：上传文件
suspend fun uploadFile(file: File) {
    val requestBody = file.asRequestBody("application/octet-stream".toMediaType())
    
    val progressBody = ProgressRequestBody(requestBody) { written, total ->
        val progress = (written * 100 / total).toInt()
        withContext(Dispatchers.Main) {
            progressBar.progress = progress // 更新 UI
        }
    }
    
    val multipartBody = MultipartBody.Builder()
        .setType(MultipartBody.FORM)
        .addFormDataPart("file", file.name, progressBody)
        .build()
    
    val request = Request.Builder()
        .url("https://api.example.com/upload")
        .post(multipartBody)
        .build()
    
    withContext(Dispatchers.IO) {
        client.newCall(request).execute()
    }
}
```

## 5. 常见面试题

### 问题1：OkHttp 的拦截器链是如何工作的？

**答案要点**：
- 责任链模式，每个拦截器处理请求的一个方面
- 拦截器按顺序执行：用户拦截器 → Retry → Bridge → Cache → Connect → 网络拦截器 → CallServer
- 每个拦截器调用 chain.proceed() 传递给下一个，可以在调用前后做处理
- 响应按相反顺序返回，形成"洋葱模型"

**记忆要点**：`拦截器链 = 洋葱模型 + 责任链。请求从外到内，响应从内到外。5个内置拦截器口诀：重桥缓连发（重试-桥接-缓存-连接-发送）`

### 问题2：OkHttp 的连接池是如何工作的？

**答案要点**：
- 复用 TCP 连接，减少三次握手 + TLS 握手的开销
- 默认最多 5 个空闲连接，存活 5 分钟
- 根据 Address（host+port+proxy）匹配可复用的连接
- 后台线程（cleanupRunnable）定期清理空闲超时的连接
- HTTP/2 同一 host 的多个请求复用同一个连接（多路复用）

**记忆要点**：`连接池 = TCP 复用池。关键参数：5个空闲、5分钟存活。类比：高速公路收费站的 ETC 通道，不用每次停车付费`

### 问题3：Retrofit 是如何实现的？

**答案要点**：
- 动态代理（Proxy.newProxyInstance）拦截接口方法调用
- 解析方法注解（@GET/@POST/@Path/@Query）生成 RequestFactory
- ServiceMethod 缓存（ConcurrentHashMap），相同方法只解析一次
- Converter 处理请求体/响应体的序列化反序列化
- CallAdapter 适配返回类型（Call/Observable/suspend）

**记忆要点**：`Retrofit = 动态代理 + 注解解析 + 缓存。核心三件套：ServiceMethod（方法描述）、Converter（数据转换）、CallAdapter（返回适配）`

### 问题4：如何实现网络请求的缓存？

**答案要点**：
- OkHttp 内置 CacheInterceptor，基于 DiskLruCache
- 遵循 HTTP 缓存协议（Cache-Control、ETag、Last-Modified）
- CacheStrategy 决定用缓存还是网络：networkRequest 和 cacheResponse 的组合
- 可通过 CacheControl.FORCE_CACHE 强制缓存，CacheControl.FORCE_NETWORK 强制网络
- 只有 GET 请求会被缓存

**记忆要点**：`CacheInterceptor 是 HTTP 缓存协议的客户端实现。判断策略看两个变量：networkRequest（要不要请网络）和 cacheResponse（有没有缓存可用）`

### 问题5：如何处理网络请求的重试？

**答案要点**：
- RetryAndFollowUpInterceptor 处理连接失败重试和重定向（最多 20 次）
- 默认只重试连接阶段的失败，不重试已发出的请求
- 可通过 retryOnConnectionFailure(false) 关闭自动重试
- 业务级重试需自定义拦截器，注意幂等性——GET 安全，POST 需谨慎
- 推荐指数退避策略避免服务端雪崩

**记忆要点**：`内置重试只管连接失败和重定向，业务重试要自己写。关键词：幂等性 + 退避策略`

### 问题6：addInterceptor 和 addNetworkInterceptor 的区别？

**答案要点**：
- addInterceptor（应用拦截器）：在 RetryAndFollowUp 之前执行，看到的是原始请求，不管有没有缓存都会执行
- addNetworkInterceptor（网络拦截器）：在 Connect 和 CallServer 之间执行，只有真正发生网络请求时才执行
- 应用拦截器适合：Token 添加、日志、请求加密
- 网络拦截器适合：修改服务端返回的 Cache-Control 头、观察真实网络数据

**记忆要点**：`应用拦截器 = 拦截器链最外层（一定执行）。网络拦截器 = 拦截器链内层（有网络请求才执行）。Token 加在应用层，Cache-Control 改在网络层`

### 问题7：Retrofit 的 ServiceMethod 缓存是如何工作的？

**答案要点**：
- 使用 ConcurrentHashMap 以 Method 为 key 缓存 ServiceMethod
- 第一次调用时解析注解创建 ServiceMethod 并放入缓存
- 后续调用直接从缓存获取，避免重复反射解析
- 双重检查锁保证线程安全
- ServiceMethod 包含 RequestFactory + CallAdapter + Converter 三大信息

**记忆要点**：`ServiceMethod 缓存 = 解析一次，使用多次。类比：编译好的字节码，不用每次都重新编译源码`

### 问题8：OkHttp 如何实现 HTTP/2 的多路复用？

**答案要点**：
- HTTP/2 在单个 TCP 连接上通过帧（Frame）传输多个请求和响应
- OkHttp 用 Http2Connection 管理连接，Http2Stream 管理单个请求流
- ConnectInterceptor 中通过 ALPN 协商确定使用 HTTP/2
- 同一 Address 的请求复用同一个 RealConnection
- 每个请求分配一个 streamId，通过 streamId 区分不同请求的帧

**记忆要点**：`HTTP/2 多路复用 = 一条路多辆车。一个 TCP 连接上多个 Stream，每个 Stream 有自己的 ID。比 HTTP/1.1 的"排队等候"快得多`
