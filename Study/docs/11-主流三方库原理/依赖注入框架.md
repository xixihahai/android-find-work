# 依赖注入框架

## 速记总结

> **一句话理解**：依赖注入就是"你不用自己造工具，告诉工具房你需要什么，它自动给你"——类不再自己 new 依赖对象，而是由外部容器创建并注入进来。Hilt 是编译时帮你写好了"取工具的代码"，Koin 是运行时从"工具登记簿"里查找。

### 核心概念速记表

| 组件 | 一句话记忆 | 生活类比 |
|------|-----------|---------|
| 依赖注入(DI) | 不要自己 new，让外部给你 | 不自己做饭，叫外卖 |
| 控制反转(IoC) | 创建对象的控制权从类内部转移到外部 | 从"自己做饭"变成"别人送饭" |
| Container/Component | DI 容器，负责创建和管理所有依赖 | 中央厨房，统一做饭配送 |
| @Inject | 标记需要注入的构造函数或字段 | 贴上"需要外卖"的标签 |
| @Module + @Provides | 告诉容器如何创建某个实例 | 菜谱，教中央厨房怎么做这道菜 |
| @Binds | 告诉容器接口用哪个实现类 | 点菜单上"红烧肉"对应后厨的"五花肉做法" |
| @Singleton | 全局只创建一个实例 | 整个公司只有一个行政前台 |
| @InstallIn | 指定 Module 安装到哪个组件（作用域） | 这个菜谱是给总店用还是分店用 |
| Scope | 实例的生命周期范围 | 这个外卖小哥只在这栋楼送 |
| Qualifier | 区分同类型的不同实例 | 同样是咖啡，@Large 和 @Small 不一样 |

## 1. 概述

依赖注入（DI）是一种设计模式，用于实现控制反转（IoC）。Android 主流 DI 框架包括 Hilt、Dagger、Koin。

### 框架对比

| 特性 | Hilt | Dagger | Koin |
|------|------|--------|------|
| 实现方式 | 编译时生成 | 编译时生成 | 运行时反射 |
| 性能 | 高 | 高 | 较低 |
| 学习成本 | 中 | 高 | 低 |
| Android 支持 | 原生支持 | 需要配置 | 原生支持 |
| 错误检测 | 编译时 | 编译时 | 运行时 |

### 2.4 Koin 原理

```kotlin
// Koin 基于 DSL 和运行时反射
// 定义模块
val appModule = module {
    single { OkHttpClient.Builder().build() }
    single { Retrofit.Builder().client(get()).build() }
    single<UserRepository> { UserRepositoryImpl(get()) }
    viewModel { MainViewModel(get()) }
}

// 启动 Koin
class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        startKoin {
            androidContext(this@MyApplication)
            modules(appModule)
        }
    }
}

// 使用
class MainActivity : AppCompatActivity() {
    private val viewModel: MainViewModel by viewModel()
    private val repository: UserRepository by inject()
}

// Koin 核心源码
// Scope.kt
class Scope(val scopeDefinition: ScopeDefinition, val id: ScopeID) {
    
    // 实例缓存
    private val _instances = hashMapOf<IndexKey, InstanceFactory<*>>()
    
    // 获取实例
    fun <T> get(clazz: KClass<*>, qualifier: Qualifier?, parameters: ParametersDefinition?): T {
        val indexKey = indexKey(clazz, qualifier)
        val instance = _instances[indexKey]
        
        return if (instance != null) {
            instance.get(InstanceContext(this, parameters)) as T
        } else {
            // 从父 Scope 查找
            _parentScope?.get(clazz, qualifier, parameters)
                ?: throw NoBeanDefFoundException("No definition found for $clazz")
        }
    }
}

// InstanceFactory.kt
sealed class InstanceFactory<T> {
    abstract fun get(context: InstanceContext): T
    
    // 单例
    class Single<T>(val definition: Definition<T>) : InstanceFactory<T>() {
        private var value: T? = null
        
        override fun get(context: InstanceContext): T {
            return value ?: synchronized(this) {
                value ?: definition(context.scope, context.parameters ?: emptyParametersHolder())
                    .also { value = it }
            }
        }
    }
    
    // 工厂
    class Factory<T>(val definition: Definition<T>) : InstanceFactory<T>() {
        override fun get(context: InstanceContext): T {
            return definition(context.scope, context.parameters ?: emptyParametersHolder())
        }
    }
}
```

## 4. 实战应用

### 4.0 为什么选 Hilt

#### 选型依据表

| 维度 | Hilt | Dagger | Koin | 手动 DI |
|------|------|--------|------|---------|
| **性能** | 编译时生成代码，运行时零反射 | 同 Hilt | 运行时反射+Map查找，略有开销 | 最快（手写代码） |
| **编译时检查** | 依赖缺失/循环依赖编译期报错 | 同 Hilt | 运行时才报错（崩溃） | 编译期（手动保证） |
| **学习成本** | 中（需理解组件层级+注解） | 高（手动写Component） | 低（DSL直观） | 低但工作量大 |
| **Android集成** | 原生支持（@AndroidEntryPoint） | 需手动配置 | 原生支持 | 手动处理一切 |
| **测试支持** | @TestInstallIn 替换依赖 | 需手动写 TestComponent | 覆盖 Module 即可 | 构造函数传入 Mock |
| **多模块支持** | @InstallIn 跨模块自动聚合 | 需手动桥接 Component | Module聚合简单 | 手动管理 |
| **社区/官方** | ★★★★★ Google官方推荐 | ★★★★ Google维护 | ★★★★ Kotlin社区活跃 | - |
| **代码量** | 中等（注解+Module） | 多（Component+Module） | 少（DSL简洁） | 最多 |

#### 迁移路径建议

```
旧方案                迁移到               关键步骤
─────────────────────────────────────────────────────────────────
手动 DI          →   Hilt              1. 添加 @HiltAndroidApp
                                       2. 把手动创建的单例移到 @Module
                                       3. 构造函数加 @Inject
                                       4. Activity 加 @AndroidEntryPoint

Dagger           →   Hilt              1. @Component → 删除（Hilt自动生成）
                                       2. @Module → 加 @InstallIn(XxxComponent::class)
                                       3. 手动注入代码 → @AndroidEntryPoint
                                       4. ViewModel → @HiltViewModel

Koin             →   Hilt              1. single { } → @Provides @Singleton
                                       2. factory { } → @Provides（不加 Scope）
                                       3. viewModel { } → @HiltViewModel
                                       4. by inject() → @Inject lateinit var
                                       5. startKoin → @HiltAndroidApp

Koin(保留)       →   优化Koin          1. 给所有 Module 写单元测试
                                          checkModules { } 提前发现问题
                                       2. 使用 koin-annotations 获得编译时检查
```

### 4.1 场景案例

#### 场景1：Repository 注入到 ViewModel

**为什么用 @HiltViewModel**：ViewModel 的创建由 ViewModelProvider.Factory 控制，你不能直接在构造函数里传参。Hilt 的 @HiltViewModel 自动生成 Factory，让你可以直接用构造函数注入依赖。

**使用依据**：@HiltViewModel 在编译时生成 `MainViewModel_Factory` 和 `MainViewModel_HiltModules`，运行时 Hilt 的 ViewModelComponent 自动使用这个 Factory 创建 ViewModel。SavedStateHandle 也自动注入。

```kotlin
// 定义 Repository 和 UseCase
class UserRepository @Inject constructor(
    private val apiService: ApiService,
    private val userDao: UserDao
) {
    suspend fun getUser(id: String): User {
        return try {
            val user = apiService.getUser(id)
            userDao.insert(user) // 缓存到本地
            user
        } catch (e: Exception) {
            userDao.getUser(id) ?: throw e // 离线降级
        }
    }
}

// ViewModel 注入 Repository
@HiltViewModel
class UserViewModel @Inject constructor(
    private val userRepository: UserRepository,
    private val savedStateHandle: SavedStateHandle  // Hilt 自动提供
) : ViewModel() {
    
    private val userId = savedStateHandle.get<String>("userId") ?: ""
    
    private val _userState = MutableStateFlow<UiState<User>>(UiState.Loading)
    val userState: StateFlow<UiState<User>> = _userState.asStateFlow()
    
    init {
        loadUser()
    }
    
    fun loadUser() {
        viewModelScope.launch {
            _userState.value = UiState.Loading
            try {
                val user = userRepository.getUser(userId)
                _userState.value = UiState.Success(user)
            } catch (e: Exception) {
                _userState.value = UiState.Error(e.message ?: "Unknown error")
            }
        }
    }
}

// Hilt 编译时生成的代码（简化版）：
// class UserViewModel_Factory(

//     private val savedStateHandleProvider: Provider<SavedStateHandle>

//         return UserViewModel(
//             userRepositoryProvider.get(),

// Activity 中使用
@AndroidEntryPoint
class UserActivity : AppCompatActivity() {
    
    // Hilt 自动使用生成的 Factory 创建 ViewModel
    private val viewModel: UserViewModel by viewModels()
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        lifecycleScope.launch {
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.userState.collect { state ->
                    when (state) {
                        is UiState.Loading -> showLoading()
                        is UiState.Success -> showUser(state.data)
                        is UiState.Error -> showError(state.message)
                    }
                }
            }
        }
    }
}
```

#### 场景2：测试时替换依赖

**为什么用 @TestInstallIn**：集成测试中需要用 FakeRepository 替换真实网络请求，不能真的去调接口。@TestInstallIn 可以在测试时替换整个 Module，而不需要修改生产代码。

**使用依据**：Hilt 的测试支持体系：@TestInstallIn 替换 Module → @UninstallModules 卸载模块 → @HiltAndroidTest 启用 Hilt 测试环境。比手动写 TestComponent 简洁得多。

```kotlin
// 生产代码：接口 + 实现
interface UserRepository {
    suspend fun getUser(id: String): User
    suspend fun getUsers(): List<User>
}

class RealUserRepository @Inject constructor(
    private val apiService: ApiService,
    private val userDao: UserDao
) : UserRepository {
    override suspend fun getUser(id: String): User = apiService.getUser(id)
    override suspend fun getUsers(): List<User> = apiService.getUsers()
}

// 生产 Module
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    @Binds
    @Singleton
    abstract fun bindUserRepository(impl: RealUserRepository): UserRepository
}

// ═══════ 测试代码 ═══════

// Fake 实现
class FakeUserRepository : UserRepository {
    private val users = mutableListOf<User>()
    
    fun addUser(user: User) { users.add(user) }
    fun clear() { users.clear() }
    
    override suspend fun getUser(id: String): User {
        return users.find { it.id == id } ?: throw NotFoundException()
    }
    
    override suspend fun getUsers(): List<User> = users.toList()
}

// 测试 Module：替换生产 Module
@Module
@TestInstallIn(
    components = [SingletonComponent::class],
```

#### 场景3：自定义 Scope

**为什么需要自定义作用域**：Hilt 内置的 Scope（@Singleton, @ActivityScoped 等）不一定满足所有场景。例如：一个登录流程包含多个 Fragment（输入手机号 → 验证码 → 设置密码），这些 Fragment 需要共享同一个 LoginSession 实例，但 LoginSession 不应该是全局单例。

**使用依据**：自定义 Scope 的本质是"定义一个依赖实例的生命周期范围"。在 Hilt 中通过自定义 Component + EntryPoint 实现，或利用已有的 ActivityRetainedComponent（跨配置变更存活）。

```kotlin
// 方案1：利用 ActivityRetainedComponent（推荐，简单场景）
// LoginSession 在整个 Activity（包括配置变更）中共享

@ActivityRetainedScoped  // 跟随 ViewModel 的生命周期，配置变更不销毁
class LoginSession @Inject constructor() {
    var phoneNumber: String = ""
    var verificationCode: String = ""
    var isVerified: Boolean = false
    
    fun reset() {
        phoneNumber = ""
        verificationCode = ""
        isVerified = false
    }
}

// 多个 Fragment 共享同一个 LoginSession
@AndroidEntryPoint
class PhoneInputFragment : Fragment() {
    @Inject lateinit var loginSession: LoginSession  // 同一个实例
    
    fun onPhoneSubmitted(phone: String) {
        loginSession.phoneNumber = phone
        navigateToVerificationFragment()
    }
}

@AndroidEntryPoint
class VerificationFragment : Fragment() {
    @Inject lateinit var loginSession: LoginSession  // 同一个实例
    
    fun onCodeVerified(code: String) {
        loginSession.verificationCode = code
        loginSession.isVerified = true
        navigateToSetPasswordFragment()
    }
}

// 方案2：利用 ViewModel 作为 Scope 容器（更 Kotlin 风格）
@HiltViewModel
class LoginViewModel @Inject constructor(
    private val loginUseCase: LoginUseCase
) : ViewModel() {
    // ViewModel 中的状态自然地在 Fragment 间共享
    private val _loginState = MutableStateFlow(LoginState())
    val loginState: StateFlow<LoginState> = _loginState.asStateFlow()
    
    fun setPhone(phone: String) {
        _loginState.update { it.copy(phoneNumber = phone) }
    }
    
    fun setVerificationCode(code: String) {
        _loginState.update { it.copy(verificationCode = code, isVerified = true) }
    }
}

// Fragment 共享 Activity 级别的 ViewModel
@AndroidEntryPoint
class PhoneInputFragment : Fragment() {
    // activityViewModels() 获取 Activity 级别的 ViewModel
    private val loginViewModel: LoginViewModel by activityViewModels()
}
```

#### 场景4：多模块项目的 DI 配置

**为什么 @InstallIn 在多模块中很重要**：大型项目通常拆分为多个 Gradle Module（:app, :feature-home, :feature-profile, :core-network, :core-database）。每个模块有自己的依赖提供，@InstallIn 让 Hilt 在编译时自动聚合所有模块的绑定。

**使用依据**：模块边界决定了依赖的可见性——:core-network 提供 Retrofit（@Singleton），:feature-home 消费 Retrofit。通过 @InstallIn 到相同的 Component，Hilt 自动完成跨模块的依赖图构建。

```kotlin
// ═══════ :core-network 模块 ═══════
// 提供网络相关依赖
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    
    @Provides
    @Singleton
    fun provideOkHttpClient(): OkHttpClient {
        return OkHttpClient.Builder()
            .addInterceptor(AuthInterceptor())
            .build()
    }
    
    @Provides
    @Singleton
    fun provideRetrofit(client: OkHttpClient): Retrofit {
        return Retrofit.Builder()
            .baseUrl(BuildConfig.BASE_URL)
            .client(client)
            .addConverterFactory(GsonConverterFactory.create())
            .build()
    }
}

// ═══════ :core-database 模块 ═══════
@Module
@InstallIn(SingletonComponent::class)
object DatabaseModule {
    
    @Provides
    @Singleton
    fun provideDatabase(@ApplicationContext context: Context): AppDatabase {
        return Room.databaseBuilder(context, AppDatabase::class.java, "app.db")
            .build()
    }
    
    @Provides
    fun provideUserDao(database: AppDatabase): UserDao = database.userDao()
}

// ═══════ :feature-home 模块 ═══════
// 消费 :core-network 和 :core-database 提供的依赖

// 本模块的 API 接口
@Module
@InstallIn(SingletonComponent::class)
object HomeApiModule {
    @Provides
    @Singleton
    fun provideHomeApiService(retrofit: Retrofit): HomeApiService {
        return retrofit.create(HomeApiService::class.java)
        // ↑ retrofit 来自 :core-network，Hilt 自动解析
    }
}

// 本模块的 Repository
@Module
@InstallIn(SingletonComponent::class)
abstract class HomeRepositoryModule {
    @Binds
    @Singleton
    abstract fun bindHomeRepository(impl: HomeRepositoryImpl): HomeRepository
}

// HomeRepositoryImpl 同时依赖网络和数据库
class HomeRepositoryImpl @Inject constructor(
    private val homeApi: HomeApiService,    // 来自 :feature-home
    private val userDao: UserDao            // 来自 :core-database
) : HomeRepository {
    // ...
}

// ═══════ :app 模块 ═══════
// 不需要手动聚合！Hilt 在编译时自动扫描所有模块的 @Module

@HiltAndroidApp
class MyApplication : Application()
// Hilt 编译时会自动发现 NetworkModule + DatabaseModule 
// + HomeApiModule + HomeRepositoryModule，构建完整的依赖图

// 多模块项目的 DI 最佳实践：
// ┌────────────────────────────────────────────────────────┐
// │ 1. :core 模块的 @Module → @InstallIn(SingletonComponent) │
// │    因为基础设施应该全局共享                              │
// │                                                        │
// │ 2. :feature 模块的 @Module → 按需选择 Component         │
// │    如果只在某个 Activity 用 → ActivityComponent         │
// │                                                        │
// │ 3. 模块间通过接口解耦                                   │
// │    :feature-home 依赖 HomeRepository 接口               │
// │    而不是 HomeRepositoryImpl 实现                       │
// │                                                        │
// │ 4. API 模块暴露接口，隐藏实现                           │
// │    在 module 的 build.gradle 中 api vs implementation   │
// └────────────────────────────────────────────────────────┘
```

## 5. 常见面试题

### 问题1：Hilt 和 Dagger 的区别是什么？

**答案要点**：
- Hilt 是 Dagger 的封装层，底层仍然是 Dagger 的代码生成
- Hilt 预定义了 Android 组件层级（SingletonComponent → ActivityComponent → FragmentComponent）
- Hilt 自动生成 Component，Dagger 需要手动定义 @Component 接口
- Hilt 通过 @AndroidEntryPoint 自动注入，Dagger 需要手动调用 inject()
- Hilt 与 Jetpack 集成更好（@HiltViewModel、Navigation 支持）
- Hilt 的 @InstallIn 简化多模块项目的依赖聚合

**记忆要点**：`Hilt = Dagger + 预设组件 + 自动注入 + Jetpack集成。关系类似于 Retrofit 和 OkHttp——Hilt 是上层封装，Dagger 是底层引擎。`

### 问题2：Hilt 的组件层级是怎样的？

**答案要点**：
- SingletonComponent（Application 生命周期，@Singleton）
- ActivityRetainedComponent（ViewModel 生命周期，配置变更不销毁，@ActivityRetainedScoped）
- ViewModelComponent（单个 ViewModel 生命周期，@ViewModelScoped）
- ActivityComponent（Activity 生命周期，@ActivityScoped）
- FragmentComponent（Fragment 生命周期，@FragmentScoped）
- ViewComponent（View 生命周期，@ViewScoped）
- ServiceComponent（Service 生命周期，@ServiceScoped）
- 子组件可以访问父组件的绑定，反之不行

**记忆要点**：`层级从上到下：Application → ActivityRetained → Activity → Fragment → View。子能访问父，父不能访问子。@Singleton 的东西哪里都能用。`

### 问题3：@Provides 和 @Binds 的区别是什么？

**答案要点**：
- @Provides：在具体方法中创建并返回实例，可以包含复杂创建逻辑（new、Builder、工厂方法）
- @Binds：声明接口和实现类的绑定关系，必须是抽象方法，参数是实现类，返回值是接口
- @Binds 生成的代码更少更高效（直接类型转换，不需要 Factory 类）
- @Provides 用于：三方库的类（不能加 @Inject）、需要 Builder 模式的类
- @Binds 用于：接口绑定实现类
- @Binds 和 @Provides 不能在同一个 object 类中（@Binds 需要 abstract class）

**记忆要点**：`@Provides = "我来创建"（方法体里写怎么创建）。@Binds = "我来绑定"（接口→实现的映射，不用写创建逻辑）。能用 @Binds 就用 @Binds，代码更少性能更好。`

### 问题4：Koin 和 Hilt 如何选择？

**答案要点**：
- Hilt 优势：编译时检查（依赖缺失编译就报错）、运行时零反射性能好、Google 官方推荐
- Koin 优势：DSL 直观简洁、学习成本低、不需要 kapt/ksp 编译速度快
- Koin 劣势：运行时才发现依赖缺失（崩溃）、有运行时开销（Map 查找 + 反射）
- 大型项目/团队项目 → Hilt（编译时安全更重要）
- 小型项目/快速原型 → Koin（开发速度更重要）
- KMP 多平台项目 → Koin（Hilt 只支持 Android）

**记忆要点**：`Hilt = 编译安全 + 性能好，适合正式项目。Koin = 上手快 + DSL 简洁，适合小项目/KMP。关键区别：编译时 vs 运行时。`

### 问题5：依赖注入的好处是什么？

**答案要点**：
- **解耦**：类不需要知道依赖如何创建，只声明"我需要什么"
- **可测试**：测试时传入 Mock/Fake 对象，不需要真实网络和数据库
- **可维护**：依赖的创建逻辑集中在 Module 中，修改一处全局生效
- **可复用**：同一个 Repository 可以被多个 ViewModel 共享（@Singleton）
- **关注分离**：业务代码专注业务逻辑，不掺杂依赖创建的样板代码
- 对比手动创建：`val repo = UserRepositoryImpl(ApiService(Retrofit(...)))` — 需要知道整条依赖链

**记忆要点**：`DI 四大好处：解耦、可测、可维护、可复用。核心原则：Don't call us, we'll call you（好莱坞原则）。你不主动创建依赖，容器给你送来。`

### 问题6：@HiltViewModel 的工作原理是什么？

**答案要点**：
- @HiltViewModel 注解触发 Hilt 的注解处理器在编译时生成 ViewModel 的 Factory
- 生成的 Factory 实现了 ViewModelProvider.Factory 接口
- Factory 的 create() 方法通过 Provider 获取所有构造函数参数（UserRepository、SavedStateHandle 等）
- HiltViewModelFactory 在 Activity/Fragment 中自动使用，无需手动传递
- SavedStateHandle 由 ViewModelComponent 自动提供（来自 CreationExtras）
- by viewModels() 委托内部使用 Hilt 注入的 Factory 创建 ViewModel

**记忆要点**：`@HiltViewModel 的本质 = 自动生成 ViewModelProvider.Factory。编译时生成 Factory → 运行时 Hilt 自动使用它创建 ViewModel → 你只需要 by viewModels() 就行。`

### 问题7：Hilt 如何处理循环依赖？

**答案要点**：
- Hilt（Dagger）在编译时检测循环依赖，直接编译报错
- 循环依赖示例：A 依赖 B，B 又依赖 A → 无法创建
- 解决方案：
  - 引入中间层：A → C ← B，C 包含共享逻辑
  - 使用 Lazy<T> 或 Provider<T> 延迟注入：`@Inject constructor(lazyB: Lazy<B>)`
  - 重新审视设计，循环依赖通常意味着架构问题
- Provider<T> 每次调用 get() 都创建新实例，Lazy<T> 只创建一次

**记忆要点**：`循环依赖 = 架构坏味道。Hilt 编译时就会报错（这是编译时检查的好处）。紧急方案用 Lazy/Provider 延迟，根本方案是重构。`

### 问题8：@Qualifier 注解的作用和使用场景？

**答案要点**：
- 当同一个类型有多个不同的实例时，用 @Qualifier 区分
- 典型场景：多个 CoroutineDispatcher（IO、Main、Default）
- 典型场景：多个 OkHttpClient（普通请求、上传专用）
- 典型场景：多个 String 类型的配置（BaseUrl、ApiKey）
- 自定义 @Qualifier 注解：`@Qualifier @Retention(BINARY) annotation class IoDispatcher`
- 在 @Provides 和 @Inject 时都要标注同一个 @Qualifier

**记忆要点**：`@Qualifier 解决"同类型多实例"的歧义。想象餐厅：同样是咖啡，你需要说"要大杯的"还是"要小杯的"。@IoDispatcher 和 @MainDispatcher 就是你的"大杯/小杯"标签。`
