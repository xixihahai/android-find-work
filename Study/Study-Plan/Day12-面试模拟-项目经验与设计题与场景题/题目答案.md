## 项目经验

#### 1. 描述你做过的最有技术挑战的项目，用 STAR 法则（项目经验）
**要点：**
- S（Situation）：公司 App 在高并发秒杀场景下崩溃率高。
- T（Task）：作为客户端负责人，需要稳定化、将崩溃率从 0.6% 降到 <0.1%。
- A（Action）：梳理链路 → 梯度降级 → 引入消息队列节流 → 端上本地队列 + 重试机制 → 优化连接池。
- R（Result）：秒杀活动期间崩溃率 0.07%，平均响应时间降低 30%，获得内部技术分享奖。

**解析：**
描述时突出数据：如使用 Firebase/自建埋点观测，定位到主线程阻塞与 WebView 崩溃两个根因；通过拆分 WebView 到独立进程 + 预加载 template 解决。强调跨端协作（与服务端制定幂等接口）。

#### 2. 你在项目中做过哪些性能优化？用数据量化结果（项目经验）
**要点：**
- 冷启动：通过延迟初始化/并行加载将应用冷启动从 2.8s 降到 1.4s。
- 渲染：RecyclerView 使用 DiffUtil + 预取，首屏掉帧率从 22% 降到 5%。
- 内存：图片缓存分级，崩溃率从 0.5‰ 降到 0.1‰。

**解析：**
量化手段：`reportFullyDrawn` 埋点、`FrameMetricsAggregator`、`Firebase Perf`。总结方法论：先监控→定位→验证→回归。

## 设计题

#### 3. 设计一个图片加载框架，要求支持三级缓存、生命周期感知、大图加载（设计题）
**要点：**
- 架构分层：RequestManager → Engine → MemoryCache/DiskCache → Fetcher/Decoder → Target。
- 三级缓存：活跃资源（引用计数）→ 内存 LruCache → 磁盘 LruCache。
- 生命周期：空 Fragment 或 LifecycleObserver 管理请求；大图加载时使用 `inSampleSize`、分片解码。

**解析：**
流程：
1. `ImageView.load(url)` 生成 `Request`，通过 RequestManager（绑定 Activity/Fragment 生命周期）提交。
2. Engine 先查 ActiveCache（引用中的 Bitmap），miss 后查 MemoryCache，再查 DiskCache。
3. 全部 miss 时调用 Fetcher（OkHttp）下载，Decoder（BitmapFactory/ImageDecoder）按需采样。
4. 生命周期：RequestManager 监听 `onStart/onStop` 暂停/恢复请求；`onDestroy` 取消并释放资源。

#### 4. 设计一个 App 的日志系统，要求支持实时上报和本地存储（设计题）
**要点：**
- 分层：API（LogKit）→ Log Buffer → Processor → Sink（本地/网络）。
- 本地存储：Rolling File（按大小/日期切分），加密 & 压缩。
- 实时上报：后台任务 `WorkManager` + 批量上传 + 重试策略。

**解析：**
日志按等级（INFO/WARN/ERROR）入队，可配置采样率。实时上报使用 `WorkManager` 结合网络约束，仅在 Wi-Fi 或充电时批量上传。为了防止敏感信息泄漏，对本地文件 AES 加密；上传前 gzip 压缩。还可以接入远程控制（开关某些 tag）。

## 场景题

#### 5. 线上用户反馈某个列表页滑动卡顿（45fps），你的排查和优化流程（场景题）
**要点：**
- 复现：开启 `adb shell dumpsys gfxinfo`, `Profile GPU Rendering`，定位掉帧区间。
- 分析：`Systrace`/`Perfetto`，关注 `Choreographer#doFrame`、`RecyclerView#onBindViewHolder`。
- 优化：DiffUtil、ViewStub、避免在 bind 中创建对象、预加载图片降级质量。

**解析：**
记录 3~5 次 profile，确认是否由于主线程阻塞还是 GPU bound。若 CPU bound，优化 Adapter 逻辑；若 GPU bound，减少阴影/圆角层级或使用硬件加速控件。最终以监控数据佐证（帧率从 45fps→58fps）。

#### 6. 线上出现大量 ANR（Service 超时），如何定位和解决？（场景题）
**要点：**
- 收集 `traces.txt`，确认是 `Service.startForeground` 还是 `onHandleIntent` 中耗时。
- 检查是否在主线程执行网络/数据库，必要时改为 `IntentService`/`WorkManager`。
- 添加守护监控：Service 内设超时 watchdog，上报堆栈。

**解析：**
常见根因：在 `onStartCommand` 中执行 I/O；前台服务未在 5s 内调用 `startForeground`。解决：在子线程或协程执行，或直接切换到 `WorkManager` 的前台任务。部署 Canary 版本验证。

#### 7. App 从 Android 13 升级到 Android 14 后，部分功能异常，排查思路？（场景题）
**要点：**
- 查看 `behavior changes` 清单，确认是否命中权限/隐私限制（如通知权限、foreground service 限制）。
- 关注 targetSdk 33→34 的 API 变动（例如精确闹钟、SAF 限制）。
- 通过 `adb logcat` + `StrictMode` 捕获兼容性告警。

**解析：**
升级步骤：1) 先在兼容模式（target 保持旧版本）运行 Android 14，观察 `logcat`；2) 升 targetSdk，逐项处理 Behavior Change，如 `foregroundServiceType` 声明、`scheduleExactAlarm` 权限等；3) 构建回归用例。必要时在 `Application` 中检测系统版本并启用 Feature Flag。
