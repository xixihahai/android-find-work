# 图片加载框架

## 速记总结

> **一句话理解**：Glide 是"智能快递分拣中心"——四级缓存像四道关卡层层拦截（活跃→内存→磁盘→网络），生命周期管理像给每个快递绑定签收人（Activity/Fragment 销毁时自动取消），图片变换像包装车间（圆角、裁剪都在这里做）。

### 核心概念速记表

| 组件 | 一句话记忆 | 生活类比 |
|------|-----------|---------|
| RequestManager | 管理请求的生命周期 | 快递站长，知道该送货还是暂停 |
| Engine | 核心加载引擎，协调缓存和解码 | 分拣中心调度台 |
| ActiveResources | 正在使用的资源（弱引用） | 你手里正在拆的快递 |
| MemoryCache | LRU 内存缓存 | 快递驿站的暂存柜 |
| DiskCache | 磁盘缓存（原始/处理后） | 仓库里的存货 |
| DecodeJob | 解码任务，负责加载和解码图片 | 拆包+质检的工人 |
| Target | 加载结果的接收者 | 收件人 |
| Transformation | 图片变换（圆角、裁剪等） | 包装车间，加工成需要的样子 |
| BitmapPool | Bitmap 对象复用池 | 回收旧包装盒循环利用 |

## 1. 概述

图片加载是 Android 开发中的常见需求，主流框架包括 Glide、Coil、Picasso 等。本文重点分析 Glide 和 Coil 的原理。

### 框架对比

| 特性 | Glide | Coil | Picasso |
|------|-------|------|---------|
| 语言 | Java | Kotlin | Java |
| 协程支持 | 否 | 是 | 否 |
| 生命周期 | 自动管理 | 自动管理 | 手动管理 |
| 缓存 | 内存+磁盘 | 内存+磁盘 | 内存+磁盘 |
| GIF 支持 | 是 | 是 | 否 |
| 包大小 | ~500KB | ~250KB | ~120KB |

// RequestManagerRetriever.java
public RequestManager get(@NonNull FragmentActivity activity) {
    if (Util.isOnBackgroundThread()) {
        return get(activity.getApplicationContext());
    }
    
    // 获取或创建 SupportRequestManagerFragment
    FragmentManager fm = activity.getSupportFragmentManager();
    return supportFragmentGet(activity, fm, null, isActivityVisible(activity));
}

private RequestManager supportFragmentGet(Context context, FragmentManager fm,
        Fragment parentHint, boolean isParentVisible) {
    // 获取或创建空白 Fragment
    SupportRequestManagerFragment current = getSupportRequestManagerFragment(fm, parentHint);
    
    RequestManager requestManager = current.getRequestManager();
    if (requestManager == null) {
        // 创建 RequestManager
        Glide glide = Glide.get(context);
        requestManager = factory.build(glide, current.getGlideLifecycle(),
                current.getRequestManagerTreeNode(), context);
        current.setRequestManager(requestManager);
    }
    return requestManager;
}

// SupportRequestManagerFragment.java
public class SupportRequestManagerFragment extends Fragment {
    private final ActivityFragmentLifecycle lifecycle;
    
    @Override
    public void onStart() {
        super.onStart();
        lifecycle.onStart();  // 通知 RequestManager
    }
    
    @Override
    public void onStop() {
        super.onStop();
        lifecycle.onStop();  // 暂停请求
    }
    
    @Override
    public void onDestroy() {
        super.onDestroy();
        lifecycle.onDestroy();  // 取消请求
    }
}

│      - 从网络下载                                           │
│                                                             │

// Engine.java - 加载流程
public <R> LoadStatus load(...) {
    // 1. 从 ActiveResources 获取
    EngineResource<?> active = loadFromActiveResources(key, isMemoryCacheable);
    if (active != null) {
        cb.onResourceReady(active, DataSource.MEMORY_CACHE);
        return null;
    }
    
    // 2. 从 MemoryCache 获取
    EngineResource<?> cached = loadFromCache(key, isMemoryCacheable);
    if (cached != null) {
        cb.onResourceReady(cached, DataSource.MEMORY_CACHE);
        return null;
    }
    
    // 3. 从磁盘或网络获取
    EngineJob<R> engineJob = engineJobFactory.build(...);
    DecodeJob<R> decodeJob = decodeJobFactory.build(...);
    
    jobs.put(key, engineJob);
    engineJob.addCallback(cb, callbackExecutor);
    engineJob.start(decodeJob);
    
    return new LoadStatus(cb, engineJob);
}

// DecodeJob.java - 解码任务
private void runWrapped() {
    switch (runReason) {
        case INITIALIZE:
            stage = getNextStage(Stage.INITIALIZE);
            currentGenerator = getNextGenerator();
            runGenerators();
            break;
        case SWITCH_TO_SOURCE_SERVICE:
            runGenerators();
            break;
        case DECODE_DATA:
            decodeFromRetrievedData();
            break;
    }
}

// 获取下一个数据源
private DataFetcherGenerator getNextGenerator() {
    switch (stage) {
        case RESOURCE_CACHE:
            return new ResourceCacheGenerator(decodeHelper, this);
        case DATA_CACHE:
            return new DataCacheGenerator(decodeHelper, this);
        case SOURCE:
            return new SourceGenerator(decodeHelper, this);
        case FINISHED:
            return null;
    }
}

### 2.5 Coil 原理

```kotlin
// Coil 基于协程实现
// ImageLoader.kt
class RealImageLoader(
    val context: Context,
    override val defaults: DefaultRequestOptions,
    val memoryCacheLazy: Lazy<MemoryCache?>,
    val diskCacheLazy: Lazy<DiskCache?>,
    val callFactory: Lazy<Call.Factory>,
    val eventListenerFactory: EventListener.Factory,
    val componentRegistry: ComponentRegistry,
    val options: ImageLoaderOptions,
    val logger: Logger?
) : ImageLoader {
    
    override fun enqueue(request: ImageRequest): Disposable {
        // 启动协程执行请求
        val job = scope.async {
            executeMain(request, REQUEST_TYPE_ENQUEUE).also { result ->
                if (result is ErrorResult) {
                    logger?.log(TAG, Log.ERROR, result.throwable.message, result.throwable)
                }
            }
        }
        return OneShotDisposable(job)
    }
    
    override suspend fun execute(request: ImageRequest): ImageResult {
        return executeMain(request, REQUEST_TYPE_EXECUTE)
    }
    
    private suspend fun executeMain(request: ImageRequest, type: Int): ImageResult {
        // 1. 检查内存缓存
        val memoryCacheKey = request.memoryCacheKey
        val memoryCacheValue = memoryCache?.get(memoryCacheKey)
        if (memoryCacheValue != null) {
            return SuccessResult(
                drawable = memoryCacheValue.bitmap.toDrawable(context.resources),
                request = request,
                dataSource = DataSource.MEMORY_CACHE
            )
        }
        
        // 2. 执行请求
        return withContext(request.dispatcher) {
            execute(request, type, memoryCacheKey)
        }
    }
}

// 使用示例
imageView.load(url) {
    crossfade(true)
    placeholder(R.drawable.placeholder)
    error(R.drawable.error)
    transformations(CircleCropTransformation())
}
```

### 3.1 Glide 请求流程

```java
// RequestBuilder.java
public ViewTarget<ImageView, TranscodeType> into(@NonNull ImageView view) {
    // 创建 Target
    ViewTarget<ImageView, TranscodeType> target = buildImageViewTarget(view, transcodeClass);
    return into(target, null, Executors.mainThreadExecutor());
}

private <Y extends Target<TranscodeType>> Y into(Y target, RequestListener<TranscodeType> targetListener,
        Executor callbackExecutor) {
    // 构建 Request
    Request request = buildRequest(target, targetListener, options, callbackExecutor);
    
    // 获取之前的 Request
    Request previous = target.getRequest();
    if (request.isEquivalentTo(previous)) {
        // 相同请求，复用
        if (!Preconditions.checkNotNull(previous).isRunning()) {
            previous.begin();
        }
        return target;
    }
    
    // 清除之前的请求
    requestManager.clear(target);
    
    // 设置新请求
    target.setRequest(request);
    requestManager.track(target, request);
    
    return target;
}

// SingleRequest.java
@Override
public void begin() {
    synchronized (requestLock) {
        if (status == Status.RUNNING) {
            return;
        }
        
        // 如果有缓存的资源
        if (Util.isValidDimensions(overrideWidth, overrideHeight)) {
            onSizeReady(overrideWidth, overrideHeight);
        } else {
            // 等待 View 测量完成
            target.getSize(this);
        }
    }
}

@Override
public void onSizeReady(int width, int height) {
    synchronized (requestLock) {
        // 开始加载
        loadStatus = engine.load(
                glideContext,
                model,
                requestOptions.getSignature(),
                this.width,
                this.height,
                requestOptions.getResourceClass(),
                transcodeClass,
                priority,
                requestOptions.getDiskCacheStrategy(),
                requestOptions.getTransformations(),
                requestOptions.isTransformationRequired(),
                requestOptions.isScaleOnlyOrNoTransform(),
                requestOptions.getOptions(),
                requestOptions.isMemoryCacheable(),
                requestOptions.getUseUnlimitedSourceGeneratorsPool(),
                requestOptions.getUseAnimationPool(),
                requestOptions.getOnlyRetrieveFromCache(),
                this,
                callbackExecutor);
    }
}

## 4. 实战应用

### 4.0 为什么选 Glide/Coil

#### 选型依据表

| 维度 | Glide | Coil | Picasso | Fresco |
|------|-------|------|---------|--------|
| **性能** | 四级缓存+BitmapPool复用，内存表现优秀 | 协程+内存磁盘缓存，轻量高效 | 两级缓存，中规中矩 | 三级缓存+Ashmem，大图优秀 |
| **包大小** | ~500KB | ~250KB | ~120KB | ~3.5MB |
| **GIF支持** | 原生支持 | 原生支持 | 不支持 | 原生支持 |
| **生命周期** | 自动管理（空白Fragment） | 自动管理（Lifecycle） | 需手动管理 | 自动管理（DraweeView） |
| **Kotlin友好** | 一般（Java写的） | 极好（Kotlin First） | 一般 | 一般 |
| **学习成本** | 中等 | 低 | 低 | 高（自定义View体系） |
| **社区活跃度** | ★★★★★ Google推荐 | ★★★★ Kotlin生态活跃 | ★★★ 维护较少 | ★★★ Meta维护 |
| **适用场景** | 通用场景首选 | 纯Kotlin项目首选 | 轻量需求 | 超多图片的社交App |

#### 迁移路径建议

```
旧方案             迁移到          关键步骤
─────────────────────────────────────────────────────────────────
Picasso        →   Glide         1. Picasso.get().load() → Glide.with().load()
                                 2. 删除手动的 tag/cancel 逻辑（Glide 自动管理）
                                 3. fit() → override(Target.SIZE_ORIGINAL)
                                 4. 迁移自定义 Transformation

Glide          →   Coil          1. Glide.with(ctx).load(url).into(iv) 
                                    → iv.load(url) { ... }
                                 2. @GlideModule → ImageLoaderFactory
                                 3. Transformation → coil.transform.Transformation

Fresco         →   Glide/Coil   1. SimpleDraweeView → ImageView（最大工作量）

                                 3. 自定义缓存策略 → DiskCacheStrategy

### 4.1 场景案例

#### 场景1：列表中加载图片闪烁/错位

**为什么会闪烁/错位**：RecyclerView 中 ViewHolder 被复用，旧的图片请求可能在新 ViewHolder 绑定新数据后才完成回调，导致错误的图片显示在错误的位置。

**使用依据**：Glide 的 into() 方法内部用 ViewTarget.setRequest()/getRequest() 给 ImageView 打了"标签"（存在 View.setTag 中）。当同一个 ImageView 调用新的 into() 时，会先取消旧 Request。

```kotlin
// ❌ 错误做法：手动设置 Bitmap，不经过 Glide
holder.imageView.setImageBitmap(null) // 手动清除
loadImageManually(url) { bitmap ->
    holder.imageView.setImageBitmap(bitmap) // 可能此时 ViewHolder 已复用
}

// ✅ 正确做法：始终使用 Glide 的 into()
Glide.with(holder.itemView)  // 注意：传 itemView 而不是 activity
    .load(item.imageUrl)
    .placeholder(R.drawable.placeholder)
    .error(R.drawable.error)
    .into(holder.imageView)
// Glide 内部流程：
// 1. into() 会调用 requestManager.clear(target) 取消旧请求
// 2. target.setRequest(newRequest) 绑定新请求到 ImageView 的 tag
// 3. 新请求开始时，旧请求的回调不会再设置图片

// ✅ 进阶：滑动时暂停加载，停下时恢复
recyclerView.addOnScrollListener(object : RecyclerView.OnScrollListener() {
    override fun onScrollStateChanged(recyclerView: RecyclerView, newState: Int) {
        when (newState) {
            RecyclerView.SCROLL_STATE_IDLE -> Glide.with(context).resumeRequests()
            else -> Glide.with(context).pauseRequests()
        }
    }
})
```

#### 场景2：超大图加载（长图预览）

**为什么用 BitmapRegionDecoder**：一张 10000x5000 的长图如果完整解码，需要 10000*5000*4 = 190MB 内存，直接 OOM。BitmapRegionDecoder 只解码可见区域，内存占用降到屏幕大小级别。

**使用依据**：Glide 的 override() 会按目标尺寸采样缩放，适合等比缩小显示整张图。但如果需要"看清局部细节"（如查看高清地图、超长聊天截图），就需要分区域解码。

```kotlin
// 方案1：Glide 采样加载（适合展示缩略图）
Glide.with(context)
    .load(largeImageUrl)
    .override(screenWidth, screenHeight)  // 按屏幕尺寸采样
    .downsample(DownsampleStrategy.FIT_CENTER)
    .into(imageView)

// 方案2：BitmapRegionDecoder（适合可缩放的大图预览）
class LargeImageView @JvmOverloads constructor(
    context: Context, attrs: AttributeSet? = null
) : View(context, attrs) {
    
    private var decoder: BitmapRegionDecoder? = null
    private val visibleRect = Rect()
    private val options = BitmapFactory.Options()
    private var currentBitmap: Bitmap? = null
    
    fun setImage(inputStream: InputStream) {
        decoder = BitmapRegionDecoder.newInstance(inputStream, false)
        options.inPreferredConfig = Bitmap.Config.RGB_565 // 省一半内存
        invalidate()
    }
    
    override fun onDraw(canvas: Canvas) {
        val decoder = this.decoder ?: return
        
        // 只解码当前可见区域
        visibleRect.set(
            scrollX, scrollY,
            scrollX + width, scrollY + height
        )
        
        // 根据缩放比例计算采样率
        options.inSampleSize = calculateSampleSize()
        
        // 回收旧 Bitmap
        currentBitmap?.recycle()
        
        // 只解码可见区域
        currentBitmap = decoder.decodeRegion(visibleRect, options)
        currentBitmap?.let { canvas.drawBitmap(it, 0f, 0f, null) }
    }
    
    private fun calculateSampleSize(): Int {
        val imageWidth = decoder?.width ?: return 1
        return (imageWidth / width).coerceAtLeast(1)
    }
}

// 实际项目中推荐使用成熟库 SubsamplingScaleImageView
// implementation 'com.davemorrissey.labs:subsampling-scale-image-view:3.10.0'
```

#### 场景3：圆角/圆形头像

**为什么用 Transformation**：直接用 Canvas 裁剪会创建新的 Bitmap，增加内存开销。Glide 的 Transformation 会利用 BitmapPool 复用 Bitmap 对象，并且变换后的结果会缓存到磁盘（DiskCacheStrategy.ALL 时），下次直接读取缓存的圆角图。

**使用依据**：Transformation 的 key 参与了缓存 key 的计算，所以 `同一张图 + 10dp圆角` 和 `同一张图 + 20dp圆角` 会缓存为两份。选择合适的缓存策略可以避免每次都重新变换。

```kotlin
// 方案1：Glide 内置 Transformation
Glide.with(context)
    .load(avatarUrl)
    .transform(CircleCrop())   // 圆形
    .into(avatarImageView)

Glide.with(context)
    .load(coverUrl)
    .transform(RoundedCorners(dpToPx(12)))  // 圆角
    .into(coverImageView)

// 多个变换组合
Glide.with(context)
    .load(url)
    .transform(CenterCrop(), RoundedCorners(dpToPx(8)))
    .into(imageView)

// 方案2：自定义 Transformation（如带边框的圆形头像）
class CircleBorderTransformation(
    private val borderWidth: Float,
    private val borderColor: Int
) : BitmapTransformation() {
    
    override fun transform(
        pool: BitmapPool, toTransform: Bitmap,
        outWidth: Int, outHeight: Int
    ): Bitmap {
        val size = minOf(toTransform.width, toTransform.height)
        val x = (toTransform.width - size) / 2
        val y = (toTransform.height - size) / 2
        
        // 从 BitmapPool 获取可复用的 Bitmap（减少 GC）
        val result = pool.get(size, size, Bitmap.Config.ARGB_8888)
        val canvas = Canvas(result)
        
        // 绘制圆形图片
        val paint = Paint(Paint.ANTI_ALIAS_FLAG)
        val shader = BitmapShader(toTransform, Shader.TileMode.CLAMP, Shader.TileMode.CLAMP)
        shader.setLocalMatrix(Matrix().apply { setTranslate(-x.toFloat(), -y.toFloat()) })
        paint.shader = shader
        
        val radius = size / 2f
        canvas.drawCircle(radius, radius, radius - borderWidth, paint)
        
        // 绘制边框
        val borderPaint = Paint(Paint.ANTI_ALIAS_FLAG).apply {
            style = Paint.Style.STROKE
            strokeWidth = borderWidth
            color = borderColor
        }
        canvas.drawCircle(radius, radius, radius - borderWidth / 2, borderPaint)
        
        return result
    }
    
    override fun updateDiskCacheKey(messageDigest: MessageDigest) {
        messageDigest.update("CircleBorder($borderWidth,$borderColor)".toByteArray())
    }
}

// 使用
Glide.with(context)
    .load(avatarUrl)
    .transform(CircleBorderTransformation(dpToPx(2f), Color.WHITE))
    .into(avatarImageView)
```

#### 场景4：预加载策略

**为什么用 preload()**：在用户即将看到图片之前提前加载到缓存，显示时直接从缓存取，实现"秒开"效果。典型场景：ViewPager 预加载下一页、列表预加载即将可见的图片。

**使用依据**：preload() 只加载到缓存不显示，比 into(imageView) 更轻量。配合 RecyclerView 的 onBindViewHolder 或 ViewPager 的 offscreenPageLimit，可以实现智能预加载。

```kotlin
// 基本预加载
Glide.with(context)
    .load(nextPageImageUrl)
    .preload()  // 加载到内存+磁盘缓存，不显示

// 指定预加载尺寸（节省内存）
Glide.with(context)
    .load(nextPageImageUrl)
    .preload(500, 500)  // 按 500x500 采样加载

// RecyclerView 预加载策略
class ImagePreloader(
    private val context: Context,
    private val imageUrls: List<String>
) : RecyclerView.OnScrollListener() {
    
    private val preloadCount = 5  // 预加载前方 5 个
    
    override fun onScrolled(recyclerView: RecyclerView, dx: Int, dy: Int) {
        val layoutManager = recyclerView.layoutManager as LinearLayoutManager
        val lastVisible = layoutManager.findLastVisibleItemPosition()
        
        // 预加载接下来的 N 个图片
        val start = lastVisible + 1
        val end = minOf(start + preloadCount, imageUrls.size)
        
        for (i in start until end) {
            Glide.with(context)
                .load(imageUrls[i])
                .preload()
        }
    }
}

// 使用
recyclerView.addOnScrollListener(ImagePreloader(this, imageUrlList))

// Glide 内置的 RecyclerViewPreloader（更优雅）
val preloader = RecyclerViewPreloader(
    Glide.with(this),
    myPreloadModelProvider,
    myPreloadSizeProvider,
    10  // maxPreload
)
recyclerView.addOnScrollListener(preloader)
```

## 5. 常见面试题

### 问题1：Glide 的四级缓存机制是怎样的？

**答案要点**：
- **ActiveResources**：正在使用的资源，弱引用存储，引用计数为0时移到 MemoryCache
- **MemoryCache**：LruCache 实现，默认大小由 MemorySizeCalculator 根据屏幕尺寸和设备内存等级动态计算，最近最少使用淘汰
- **DiskCache**：DiskLruCache 实现，默认 250MB，分 DATA（原始）和 RESOURCE（处理后）两种
- 查找顺序：Active → Memory → ResourceDisk → DataDisk → Network
- 缓存 Key 由 url + 尺寸 + Transformation + 签名等多因素组成

**记忆要点**：`四级缓存口诀：活内磁网（Active-Memory-Disk-Network）。Active 用弱引用是为了不阻止 GC，Memory 用 LRU 是为了控制大小。`

### 问题2：Glide 如何管理生命周期？

**答案要点**：
- 通过 RequestManagerRetriever 添加空白 Fragment（SupportRequestManagerFragment）到 Activity/Fragment
- Fragment 生命周期回调通过 ActivityFragmentLifecycle 通知 RequestManager
- onStart → resumeRequests（恢复暂停的请求）
- onStop → pauseRequests（暂停进行中的请求，节省带宽和电量）
- onDestroy → destroy（取消所有请求 + 清理资源，防止内存泄漏）
- 后台线程调用 with() 会使用 Application Context，不跟踪生命周期

**记忆要点**：`空白 Fragment 是"生命周期哨兵"。关键：with(activity) 绑定 Activity 生命周期，with(applicationContext) 跟随应用生命周期。列表 item 用 with(itemView) 更精准。`

### 问题3：Glide 和 Coil 的区别是什么？

**答案要点**：
- Coil 基于 Kotlin 协程，Glide 基于线程池 + Handler
- Coil 包更小（~250KB vs ~500KB），API 更简洁（imageView.load(url)）
- Glide 功能更丰富（GIF、Bitmap Pool），生态更完善（更多 Transform 库）
- Coil 更适合纯 Kotlin 项目，Compose 支持更好
- Glide 的生命周期管理用空白 Fragment，Coil 直接用 Lifecycle
- Coil 缓存 key 默认不包含尺寸信息，一张图只缓存一份

**记忆要点**：`Glide = Java时代的王者，功能全面。Coil = Kotlin时代的新星，轻量简洁。新的纯Kotlin项目选Coil，老项目或需要GIF/复杂变换选Glide。`

### 问题4：如何优化图片加载性能？

**答案要点**：
- 使用 RGB_565 代替 ARGB_8888（省一半内存，但不支持透明度）
- 设置合适的缓存策略（DiskCacheStrategy.ALL 缓存原始+处理后）
- 使用 thumbnail(0.3f) 先加载 30% 质量缩略图再加载高清图
- 列表滑动时 pauseRequests()，停下时 resumeRequests()
- 预加载即将显示的图片（preload）
- override() 指定加载尺寸，避免加载超出 ImageView 大小的图片
- 使用 BitmapPool 复用 Bitmap 对象，减少 GC

**记忆要点**：`性能优化三板斧：缩（override缩小尺寸）、存（合理缓存策略）、控（滑动暂停+预加载）`

### 问题5：Glide 如何处理大图？

**答案要点**：
- 自动根据 ImageView 大小计算 inSampleSize 采样缩放
- 使用 override(width, height) 指定加载尺寸
- 超大图（长图/地图）使用 BitmapRegionDecoder 分区域解码
- DownsampleStrategy 控制采样策略（FIT_CENTER、CENTER_INSIDE 等）
- 建议配合 SubsamplingScaleImageView 实现可缩放大图预览

**记忆要点**：`Glide 自动采样解决"大图缩小显示"问题。BitmapRegionDecoder 解决"大图看局部细节"问题。两者适用场景不同。`

### 问题6：Glide 的 into() 方法内部做了什么？

**答案要点**：
- 创建 ViewTarget 包装 ImageView
- 通过 buildRequest() 创建 SingleRequest
- 检查 Target 上是否有旧 Request（getRequest）：相同则复用，不同则取消旧的
- target.setRequest(request) 将 Request 存入 ImageView 的 tag（setTag）
- requestManager.track(target, request) 开始跟踪和执行
- 这就是为什么 RecyclerView 中图片不会错位——每次 into() 会取消旧请求

**记忆要点**：`into() = 取消旧请求 + 绑定新请求到 View tag + 开始加载。这是解决列表图片错位的核心机制。`

### 问题7：Glide 的 BitmapPool 是什么？有什么作用？

**答案要点**：
- BitmapPool 是 Bitmap 对象的复用池，基于 LRU 淘汰策略
- 当 Bitmap 不再使用时，放入 Pool 而不是让 GC 回收
- 下次需要相同配置（宽高+Config）的 Bitmap 时，从 Pool 获取复用
- 减少频繁创建和销毁 Bitmap 带来的 GC 压力
- Transformation 中通过 pool.get() 获取可复用的 Bitmap

**记忆要点**：`BitmapPool = Bitmap 的"二手市场"。不要的 Bitmap 不扔，放进去给别人用。核心收益：减少 GC 抖动（尤其列表滑动时）。`

### 问题8：Glide 的缓存 Key 是如何生成的？为什么同一张图可能有多份缓存？

**答案要点**：
- 缓存 Key 由多个因素组成：URL + 宽度 + 高度 + Transformation + Signature + ...
- 同一张 URL，不同尺寸的 ImageView 加载后会生成不同的缓存（因为尺寸不同）
- 同一张 URL，不同 Transformation（圆形 vs 圆角）也会生成不同缓存
- DATA 缓存（原始数据）的 Key 只看 URL，不含尺寸和变换
- RESOURCE 缓存（处理后数据）的 Key 包含尺寸和变换
- 可以通过 signature(ObjectKey("v2")) 强制刷新缓存

**记忆要点**：`缓存 Key = URL + 尺寸 + 变换 + 签名。理解这个就理解了为什么同一张图在不同地方加载会缓存多份——因为 Key 不同。`
