# 响应式编程

## 速记总结

> **一句话理解**：响应式编程就是"数据流水线"——数据像水一样从上游流向下游，中间经过各种管道（操作符）过滤、转换、合并，最终流到终点（观察者）。你不需要主动去取水，水来了自动通知你。

### 核心概念速记表

| 组件 | 一句话记忆 | 生活类比 |
|------|-----------|---------|
| Observable/Flow | 数据的生产者，发射数据流 | 自来水厂，持续供水 |
| Observer/Collector | 数据的消费者，接收并处理数据 | 你家的水龙头，接水用 |
| Operator | 数据的中间处理器 | 水管中间的过滤器、分流器 |
| Scheduler/Dispatcher | 指定在哪个线程执行 | 决定水从哪条管道走 |
| subscribeOn | 指定上游（数据发射）的线程 | 决定水厂在哪里建 |
| observeOn/flowOn | 指定下游（数据接收）的线程 | 决定水龙头装在哪里 |
| Disposable/Job | 订阅关系的句柄，用于取消 | 水管的总阀门，关了就断水 |
| 背压(Backpressure) | 上游太快下游处理不过来的问题 | 水厂供水太猛，管道爆了 |

### RxJava 线程切换原理图解

```
  Observable.create { emitter -> emitter.onNext(data) }  // 数据源
      .subscribeOn(Schedulers.io())      // ① 指定上游线程
      .map { transform(it) }            // 在 io 线程执行
      .observeOn(MainScheduler)          // ② 切换下游线程
      .filter { it.isValid }            // 在 main 线程执行
      .subscribe { updateUI(it) }       // 在 main 线程执行

  ──── subscribeOn 原理 ────────────────────────────────────────

  subscribeOn(Schedulers.io()) 做了什么？
  
  ┌──────────────────────────────────────────────────┐
  │  ObservableSubscribeOn                           │
  │                                                  │
  │  subscribeActual(observer) {                     │
  │    // 在指定线程执行 source.subscribe()           │
  │    scheduler.scheduleDirect {                    │
  │      source.subscribe(observer)  // ← 整个订阅链  │
  │    }                             //   都在io线程   │
  │  }                                               │
  │                                                  │
  │  为什么只有第一个 subscribeOn 生效？               │
  │  因为订阅是从下游向上游传递的：                    │
  │  最外层的 subscribeOn 先执行，把整个订阅链         │
  │  切到它指定的线程，内层的切换被覆盖了              │
  └──────────────────────────────────────────────────┘

  ──── observeOn 原理 ──────────────────────────────────────────

  observeOn(MainScheduler) 做了什么？

  ┌──────────────────────────────────────────────────┐
  │  ObservableObserveOn                             │
  │                                                  │
  │  ObserveOnObserver.onNext(T t) {                 │
  │    queue.offer(t)     // 数据放入队列             │
  │    worker.schedule {  // 在指定线程取出并分发      │
  │      val v = queue.poll()                        │
  │      downstream.onNext(v)  // ← 下游在新线程收到  │
  │    }                                             │
  │  }                                               │
  │                                                  │
  │  为什么 observeOn 可以多次切换？                   │
  │  因为每个 observeOn 只影响它下游的 observer，      │
  │  多个 observeOn 形成多次线程切换：                 │
  │  io → observeOn(computation) → computation       │
  │       → observeOn(main) → main                   │
  └──────────────────────────────────────────────────┘
```

### Flow vs RxJava vs LiveData 详细对比表

| 维度 | RxJava | Kotlin Flow | LiveData |
|------|--------|-------------|----------|
| **冷/热** | Observable(热)/Flowable(按需) | Flow(冷)/StateFlow,SharedFlow(热) | 热（始终持有最新值） |
| **线程切换** | subscribeOn/observeOn | flowOn/collect 所在协程 | 只在主线程观察 |
| **取消机制** | Disposable.dispose() | 协程取消自动取消 | Lifecycle 自动取消 |
| **背压处理** | Flowable + 5种策略 | buffer/conflate/collectLatest | 无（始终最新值） |
| **操作符数量** | 400+ | 50+（但可用suspend扩展） | ~10个（Transformations） |
| **错误处理** | onError + 全局 ErrorHandler | catch {} + 协程 ExceptionHandler | 无内置错误通道 |
| **生命周期** | 需手动管理（CompositeDisposable） | repeatOnLifecycle 自动管理 | 原生支持 |
| **多值发射** | 原生支持 | 原生支持 | 不支持（只保留最新） |
| **学习成本** | 高（操作符多、线程模型复杂） | 中（需理解协程） | 低 |
| **包大小** | ~2.4MB | 协程库~1.5MB（已引入） | ~50KB |
| **适用场景** | 复杂异步流、大量操作符组合 | 新项目的首选异步方案 | 简单的UI状态观察 |
| **推荐度(2024+)** | 维护旧项目 | 新项目首选 | 配合 ViewModel 使用 |

## 1. 概述

响应式编程是一种基于数据流和变化传播的编程范式。Android 中主要使用 RxJava 和 Kotlin Flow。

```kotlin
    emitter.onNext(1)
    emitter.onNext(2)
    emitter.onNext(3)

// 订阅

    .subscribeOn(Schedulers.io())
    .observeOn(AndroidSchedulers.mainThread())
```

### 2.3 RxJava 原理

```java
// Observable.java
public abstract class Observable<T> implements ObservableSource<T> {
    
    // 创建 Observable
    public static <T> Observable<T> create(ObservableOnSubscribe<T> source) {
        return new ObservableCreate<>(source);
    }
    
    // 订阅
    @Override
    public final void subscribe(Observer<? super T> observer) {
        // 包装 Observer
        observer = RxJavaPlugins.onSubscribe(this, observer);
        // 调用 subscribeActual
        subscribeActual(observer);
    }
    
    protected abstract void subscribeActual(Observer<? super T> observer);
}

// ObservableCreate.java
public final class ObservableCreate<T> extends Observable<T> {
    final ObservableOnSubscribe<T> source;
    
    @Override
    protected void subscribeActual(Observer<? super T> observer) {
        // 创建 Emitter
        CreateEmitter<T> parent = new CreateEmitter<>(observer);
        // 通知订阅
        observer.onSubscribe(parent);
        // 执行订阅逻辑
        source.subscribe(parent);
    }
}

// 装饰器模式 - map 操作符
public final class ObservableMap<T, U> extends AbstractObservableWithUpstream<T, U> {
    final Function<? super T, ? extends U> function;
    
    @Override
    protected void subscribeActual(Observer<? super U> observer) {
        // 包装 Observer
        source.subscribe(new MapObserver<>(observer, function));
    }
    
    static final class MapObserver<T, U> implements Observer<T> {
        final Observer<? super U> downstream;
        final Function<? super T, ? extends U> mapper;
        
        @Override
        public void onNext(T t) {
            U v = mapper.apply(t);
            downstream.onNext(v);
        }
    }
}
```

### 2.5 EventBus 原理

```java
// EventBus.java
public class EventBus {
    // 订阅者方法缓存
    private final Map<Class<?>, CopyOnWriteArrayList<Subscription>> subscriptionsByEventType;
    // 订阅者的事件类型
    private final Map<Object, List<Class<?>>> typesBySubscriber;
    
    // 注册
    public void register(Object subscriber) {
        Class<?> subscriberClass = subscriber.getClass();
        // 查找订阅方法
        List<SubscriberMethod> subscriberMethods = subscriberMethodFinder.findSubscriberMethods(subscriberClass);
        synchronized (this) {
            for (SubscriberMethod subscriberMethod : subscriberMethods) {
                subscribe(subscriber, subscriberMethod);
            }
        }
    }
    
    // 订阅
    private void subscribe(Object subscriber, SubscriberMethod subscriberMethod) {
        Class<?> eventType = subscriberMethod.eventType;
        Subscription newSubscription = new Subscription(subscriber, subscriberMethod);
        
        CopyOnWriteArrayList<Subscription> subscriptions = subscriptionsByEventType.get(eventType);
        if (subscriptions == null) {
            subscriptions = new CopyOnWriteArrayList<>();
            subscriptionsByEventType.put(eventType, subscriptions);
        }
        subscriptions.add(newSubscription);
    }
    
    // 发送事件
    public void post(Object event) {
        PostingThreadState postingState = currentPostingThreadState.get();
        List<Object> eventQueue = postingState.eventQueue;
        eventQueue.add(event);
        
        while (!eventQueue.isEmpty()) {
            postSingleEvent(eventQueue.remove(0), postingState);
        }
    }
    
    private void postSingleEvent(Object event, PostingThreadState postingState) {
        Class<?> eventClass = event.getClass();
        // 查找订阅者
        CopyOnWriteArrayList<Subscription> subscriptions = subscriptionsByEventType.get(eventClass);
        if (subscriptions != null) {
            for (Subscription subscription : subscriptions) {
                postToSubscription(subscription, event, postingState.isMainThread);
            }
        }
    }
    
    // 根据线程模式分发
    private void postToSubscription(Subscription subscription, Object event, boolean isMainThread) {
        switch (subscription.subscriberMethod.threadMode) {
            case POSTING:
                invokeSubscriber(subscription, event);
                break;
            case MAIN:
                if (isMainThread) {
                    invokeSubscriber(subscription, event);
                } else {
                    mainThreadPoster.enqueue(subscription, event);
                }
                break;
            case BACKGROUND:
                if (isMainThread) {
                    backgroundPoster.enqueue(subscription, event);
                } else {
                    invokeSubscriber(subscription, event);
                }
                break;
            case ASYNC:
                asyncPoster.enqueue(subscription, event);
                break;
        }
    }
}

// 使用示例
```

### 3.1 RxJava 线程切换

```java
// subscribeOn - 指定订阅线程
public final Observable<T> subscribeOn(Scheduler scheduler) {
    return new ObservableSubscribeOn<>(this, scheduler);
}

// ObservableSubscribeOn.java
public final class ObservableSubscribeOn<T> extends AbstractObservableWithUpstream<T, T> {
    final Scheduler scheduler;
    
    @Override
    protected void subscribeActual(Observer<? super T> observer) {
        SubscribeOnObserver<T> parent = new SubscribeOnObserver<>(observer);
        observer.onSubscribe(parent);
        // 在指定线程执行订阅
        parent.setDisposable(scheduler.scheduleDirect(new SubscribeTask(parent)));
    }
    
    final class SubscribeTask implements Runnable {
        @Override
        public void run() {
            source.subscribe(parent);
        }
    }
}

// observeOn - 指定观察线程
public final Observable<T> observeOn(Scheduler scheduler) {
    return new ObservableObserveOn<>(this, scheduler, false, bufferSize());
}

// ObservableObserveOn.java
public final class ObservableObserveOn<T> extends AbstractObservableWithUpstream<T, T> {
    @Override
    protected void subscribeActual(Observer<? super T> observer) {
        Scheduler.Worker w = scheduler.createWorker();
        source.subscribe(new ObserveOnObserver<>(observer, w, delayError, bufferSize));
    }
    
    static final class ObserveOnObserver<T> implements Observer<T>, Runnable {
        @Override
        public void onNext(T t) {
            // 加入队列
            queue.offer(t);
            schedule();
        }
        
        void schedule() {
            // 在指定线程执行
            worker.schedule(this);
        }
        
        @Override
        public void run() {
            // 从队列取出并分发
            T v = queue.poll();
            downstream.onNext(v);
        }
    }
}
```

## 4. 实战应用

### 4.0 为什么选响应式编程框架

#### 选型依据表

| 维度 | RxJava | Kotlin Flow | LiveData | 回调/Listener |
|------|--------|-------------|----------|--------------|
| **性能** | 对象创建多，有一定开销 | 协程挂起恢复，开销小 | 极轻量 | 最轻量 |
| **可组合性** | ★★★★★ 操作符极丰富 | ★★★★ 够用+可扩展 | ★★ 有限 | ★ 回调地狱 |
| **维护性** | 链式调用可读性好，但复杂链难调试 | 协程+Flow简洁直观 | 简单场景好 | 复杂场景噩梦 |
| **学习成本** | 高（marble图、操作符选择） | 中（需理解协程） | 低 | 低 |
| **社区活跃度** | ★★★ 成熟但趋下降 | ★★★★★ Kotlin官方力推 | ★★★★ Jetpack标配 | - |

#### 迁移路径建议

```
旧方案                    迁移到                   关键步骤
─────────────────────────────────────────────────────────────────
AsyncTask            →   协程+Flow             1. doInBackground → withContext(IO)
                                               2. onPostExecute → 直接在主协程写
                                               3. publishProgress → Flow.emit

回调嵌套             →   RxJava/Flow           1. 每个异步操作封装为 Observable/Flow
                                               2. flatMap 替代嵌套回调
                                               3. zip 替代计数器等待多个回调

RxJava               →   Kotlin Flow           1. Observable → Flow
                                               2. subscribeOn(io) → flowOn(IO)
                                               3. observeOn(main) → collect 在主协程
                                               4. CompositeDisposable → 协程自动取消
                                               5. Subject → MutableSharedFlow
                                               6. BehaviorSubject → MutableStateFlow

LiveData(复杂场景)   →   StateFlow             1. MutableLiveData → MutableStateFlow
                                               2. observe → collectAsState / collect
                                               3. Transformations.map → flow.map
                                               4. MediatorLiveData → combine
```

### 4.1 场景案例

#### 场景1：搜索框防抖（debounce）

**为什么用响应式而不是 Handler.postDelayed**：Handler.postDelayed 需要手动 removeCallbacks，多个地方用就需要多个 Handler + Runnable，代码散落各处。响应式的 debounce 把"防抖"这个逻辑内聚在数据流管道中，一行代码搞定。

**使用依据**：
- debounce：用户停止输入 300ms 后才发请求，减少无效请求
- distinctUntilChanged：相同的搜索词不重复请求
- switchMap/flatMapLatest：新请求来了自动取消上一个未完成的请求

```kotlin
// ❌ Handler 方案：散落、难维护
class SearchActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper())
    private var searchRunnable: Runnable? = null
    
    fun onTextChanged(text: String) {
        searchRunnable?.let { handler.removeCallbacks(it) }
        searchRunnable = Runnable { doSearch(text) }
        handler.postDelayed(searchRunnable!!, 300)
    }
    // 还需要在 onDestroy 中 removeCallbacksAndMessages(null)
    // 还需要处理"相同词不重复搜索"的逻辑
    // 还需要处理"取消上一个未完成请求"的逻辑
}

// ✅ RxJava 方案：声明式、内聚
searchEditText.textChanges()                     // 监听文本变化
    .debounce(300, TimeUnit.MILLISECONDS)        // 防抖 300ms
    .map { it.toString().trim() }                // 转 String
    .filter { it.length >= 2 }                   // 至少 2 个字符
    .distinctUntilChanged()                      // 相同文本不重复
    .switchMap { query ->                        // 新请求自动取消旧请求
        apiService.search(query)
            .onErrorReturnItem(emptyList())       // 搜索失败返回空
    }
    .subscribeOn(Schedulers.io())
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe { results -> adapter.submitList(results) }

// ✅ Kotlin Flow 方案
editText.textChanges()
    .debounce(300)
    .map { it.toString().trim() }
    .filter { it.length >= 2 }
    .distinctUntilChanged()
    .flatMapLatest { query ->                    // Flow 版的 switchMap
        flow { emit(apiService.search(query)) }
            .catch { emit(emptyList()) }
    }
    .flowOn(Dispatchers.IO)
    .onEach { results -> adapter.submitList(results) }
    .launchIn(lifecycleScope)
```

#### 场景2：多个接口并行请求合并结果（zip/combine）

**为什么用 zip/combine 而不是回调计数器**：传统做法需要一个计数器，每个回调 +1，全部完成才合并——代码丑陋、容易出错（忘记处理某个失败、线程安全问题）。zip/combine 声明式地描述"等所有数据到齐后合并"。

**使用依据**：
- zip：等所有 Observable/Flow 都发射一次后合并（一对一配对）
- combine：任意一个 Flow 发射新值就合并（取各 Flow 最新值）
- 适用：首页加载需要同时请求 Banner + 推荐列表 + 用户信息，全部完成后一起渲染

```kotlin
// ❌ 回调计数器方案：丑陋、易出错
var banner: Banner? = null
var recommendations: List<Item>? = null
var userInfo: User? = null
var completedCount = 0

fun checkAllCompleted() {
    if (++completedCount == 3) {
        renderPage(banner!!, recommendations!!, userInfo!!)
    }
}
// 还需要处理任意一个失败的情况...线程安全...

// ✅ RxJava zip 方案
Observable.zip(
    apiService.getBanner(),
    apiService.getRecommendations(),
    apiService.getUserInfo()
) { banner, recommendations, userInfo ->
    HomePageData(banner, recommendations, userInfo)
}
.subscribeOn(Schedulers.io())
.observeOn(AndroidSchedulers.mainThread())
.subscribe(
    { data -> renderPage(data) },
    { error -> showError(error) }
)

// ✅ Kotlin Flow combine 方案（任一 Flow 更新都会触发合并）
combine(
    bannerFlow,
    recommendationsFlow,
    userInfoFlow
) { banner, recommendations, userInfo ->
    HomePageData(banner, recommendations, userInfo)
}
.catch { error -> emit(HomePageData.error(error)) }
.collect { data -> renderPage(data) }

// ✅ 协程并行方案（更简洁，推荐）
viewModelScope.launch {
    try {
        val banner = async { apiService.getBanner() }
        val recommendations = async { apiService.getRecommendations() }
        val userInfo = async { apiService.getUserInfo() }
        
        val data = HomePageData(
            banner.await(),
            recommendations.await(),
            userInfo.await()
        )
        _uiState.value = data
    } catch (e: Exception) {
        _uiState.value = HomePageData.error(e)
    }
}
```

#### 场景3：接口轮询（interval + flatMap）

**为什么不用 Timer/ScheduledExecutor**：Timer 在任务抛异常时整个 Timer 挂掉，ScheduledExecutor 需要手动管理生命周期。响应式方案自带错误处理、生命周期绑定、操作符组合能力。

**使用依据**：
- interval：周期性发射事件
- flatMap/switchMap：把每次 tick 转化为 API 请求
- takeUntil/takeWhile：满足条件自动停止轮询
- retry：单次请求失败不影响后续轮询

```kotlin
// ❌ Timer 方案：异常不安全、生命周期难管理
val timer = Timer()
timer.scheduleAtFixedRate(object : TimerTask() {
    override fun run() {
        // 这里抛异常 Timer 就死了
        val status = api.getOrderStatus(orderId)
        runOnUiThread { updateStatus(status) }
    }
}, 0, 5000)
// 还需要在 onDestroy 中 timer.cancel()

// ✅ RxJava 方案
Observable.interval(0, 5, TimeUnit.SECONDS)      // 每 5 秒
    .flatMapSingle { apiService.getOrderStatus(orderId) }
    .takeUntil { it.status == "COMPLETED" }       // 完成后自动停止
    .retry(3)                                      // 单次失败重试
    .subscribeOn(Schedulers.io())
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe(
        { status -> updateOrderUI(status) },
        { error -> showError(error) }
    )

// ✅ Kotlin Flow 方案
fun pollOrderStatus(orderId: String): Flow<OrderStatus> = flow {
    while (true) {
        val status = apiService.getOrderStatus(orderId)
        emit(status)
        if (status.status == "COMPLETED") break
        delay(5000)  // 协程的 delay 不阻塞线程
    }
}
.retry(3) { e ->
    e is IOException   // 只重试网络异常
}
.flowOn(Dispatchers.IO)

// 在 ViewModel 中使用
viewModelScope.launch {
    pollOrderStatus(orderId)
        .collect { status -> _orderState.value = status }
}
// viewModelScope 取消时自动停止轮询，无需手动管理
```

#### 场景4：错误重试策略（retryWhen）——指数退避实现

**为什么用 retryWhen 而不是简单 retry**：简单 retry(3) 是"失败就立刻重试"，在服务端故障时会产生"重试风暴"加重服务器负担。指数退避（1s → 2s → 4s → 8s...）给服务器恢复时间。

**使用依据**：
- 指数退避是分布式系统的标准做法（AWS/Google 官方推荐）
- retryWhen 可以根据错误类型决定是否重试（网络错误重试，业务错误不重试）
- 加上随机抖动（jitter）避免多个客户端同一时刻重试

```kotlin
// ✅ RxJava 指数退避重试
fun <T> Observable<T>.retryWithExponentialBackoff(
    maxRetries: Int = 3,
    initialDelay: Long = 1000,
    maxDelay: Long = 30000
): Observable<T> = retryWhen { errors ->
    errors
        .zipWith(Observable.range(1, maxRetries)) { error, retryCount ->
            if (error is IOException) {
                retryCount  // 网络错误 → 重试
            } else {
                throw error  // 业务错误 → 直接抛出
            }
        }
        .flatMap { retryCount ->
            val delay = minOf(
                initialDelay * 2.0.pow(retryCount - 1).toLong(),
                maxDelay
            )
            // 加随机抖动，避免同时重试
            val jitter = (delay * 0.2 * Random.nextDouble()).toLong()
            Observable.timer(delay + jitter, TimeUnit.MILLISECONDS)
        }
}

// 使用
apiService.getData()
    .retryWithExponentialBackoff(maxRetries = 4)
    .subscribeOn(Schedulers.io())
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe { data -> updateUI(data) }

// ✅ Kotlin Flow 指数退避重试
fun <T> Flow<T>.retryWithExponentialBackoff(
    maxRetries: Int = 3,
    initialDelay: Long = 1000,
    maxDelay: Long = 30000
): Flow<T> = retry(maxRetries.toLong()) { cause ->
    if (cause is IOException) {
        val retryCount = maxRetries  // Flow 的 retry 自动跟踪次数
        val delay = minOf(
            initialDelay * 2.0.pow(retryCount - 1).toLong(),
            maxDelay
        )
        val jitter = (delay * 0.2 * Random.nextDouble()).toLong()
        delay(delay + jitter)
        true  // 返回 true 表示重试
    } else {
        false // 非网络错误不重试
    }
}

// 使用
flow { emit(apiService.getData()) }
    .retryWithExponentialBackoff()
    .flowOn(Dispatchers.IO)
    .collect { data -> updateUI(data) }
```

## 5. 常见面试题

### 问题1：RxJava 的核心思想是什么？

**答案要点**：
- 观察者模式：Observable（被观察者）和 Observer（观察者）的订阅关系
- 函数式编程：操作符链式调用，每个操作符返回新的 Observable（装饰器模式）
- 异步编程：Scheduler 实现线程切换，解耦数据生产和消费的线程
- 响应式：数据流驱动，上游数据变化自动推送给下游

**记忆要点**：`RxJava = 观察者模式（订阅关系）+ 装饰器模式（操作符包装）+ 策略模式（Scheduler切线程）。三个设计模式串起来就是 RxJava 的骨架。`

### 问题2：subscribeOn 和 observeOn 的区别是什么？

**答案要点**：
- subscribeOn：指定整个订阅链（数据发射）的线程，只有第一个生效
  - 原理：把 source.subscribe() 放到指定 Scheduler 的线程中执行
  - 为什么只有第一个生效：订阅从下游向上游传递，最外层的 subscribeOn 最先执行
- observeOn：指定下游（数据接收）的线程，可以多次切换
  - 原理：把 onNext() 的数据放入队列，再在指定线程的 Worker 中取出分发
  - 每个 observeOn 只影响它下游的操作符
- 经典组合：subscribeOn(io) + observeOn(main) = IO 线程请求数据，主线程更新 UI

**记忆要点**：`subscribeOn 管"从哪里发"（上游），只认第一个。observeOn 管"在哪里收"（下游），可以反复切。`

### 问题3：RxJava 如何处理背压？

**答案要点**：
- 背压（Backpressure）：上游发射速度 > 下游处理速度，导致数据积压
- Observable 不支持背压，Flowable 支持
- 五种背压策略：
  - BUFFER：缓存所有数据（可能 OOM）
  - DROP：丢弃新数据
  - LATEST：只保留最新数据
  - ERROR：抛出 MissingBackpressureException
  - MISSING：不做处理，交给下游自己处理
- Kotlin Flow 的背压方案：buffer()（缓存）、conflate()（合并只保留最新）、collectLatest()（取消旧的处理新的）

**记忆要点**：`背压 = 生产快消费慢。Flowable 有 5 种策略。实际最常用 LATEST（传感器数据）和 BUFFER（日志收集）。Flow 用 conflate/collectLatest。`

### 问题4：EventBus 的原理是什么？

**答案要点**：
- 发布-订阅模式（不同于观察者模式——有中间的事件总线解耦）
- 注册：反射/注解处理器查找 @Subscribe 方法，存入 Map<EventType, List<Subscription>>
- 发送：从 Map 中找到对应事件类型的所有订阅者
- 根据 ThreadMode 分发：POSTING（当前线程）、MAIN（主线程）、BACKGROUND（后台）、ASYNC（异步新线程）
- 粘性事件（Sticky）：先发后订也能收到

**记忆要点**：`EventBus = 一个全局 Map<事件类型, 订阅者列表>。注册时往 Map 里加，发送时从 Map 里找。4 种 ThreadMode 决定在哪执行。`

### 问题5：RxJava 和 Kotlin Flow 如何选择？

**答案要点**：
- 新项目推荐 Kotlin Flow：与协程原生集成，自动取消，学习成本低
- RxJava 操作符更丰富（400+ vs 50+），复杂异步流编排更强
- Flow 的操作符函数可以调用 suspend 函数，这是 RxJava 做不到的
- Flow 是冷流（有人 collect 才执行），RxJava 的 Observable 默认是热的
- 老项目有大量 RxJava 代码不需要强行迁移，两者可以通过 kotlinx-coroutines-rx2 桥接
- LiveData 适合简单的 UI 状态，复杂场景用 StateFlow 替代

**记忆要点**：`选择原则：新项目 → Flow，老项目 → 不急迁移。Flow 胜在协程集成和自动取消，RxJava 胜在操作符丰富和社区积累。`

### 问题6：flatMap、concatMap、switchMap 的区别？

**答案要点**：
- **flatMap**：把每个元素映射为新的 Observable 并合并，不保证顺序（并发执行）
- **concatMap**：和 flatMap 类似但保证顺序（上一个完成才开始下一个）
- **switchMap**：新的 Observable 发射时自动取消上一个未完成的
- 选择依据：
  - 搜索框 → switchMap（只关心最新搜索结果）
  - 分页加载 → concatMap（保证页码顺序）
  - 并行处理 → flatMap（不关心顺序，追求速度）

**记忆要点**：`flat=打乱、concat=排队、switch=切换。搜索用 switch（新的来了旧的不要），分页用 concat（顺序重要），批量处理用 flat（速度优先）。`

### 问题7：如何避免 RxJava 的内存泄漏？

**答案要点**：
- 使用 CompositeDisposable 统一管理，onDestroy 中 clear()
- 使用 AutoDispose/RxLifecycle 自动绑定生命周期
- Kotlin Flow 方案：在 lifecycleScope/viewModelScope 中 collect，自动取消
- repeatOnLifecycle 确保只在前台时收集 Flow
- 避免匿名内部类持有 Activity 引用（改用 WeakReference 或 ViewModel）

**记忆要点**：`RxJava 泄漏根因：订阅关系持有外部引用。解决：CompositeDisposable（手动管理）或 AutoDispose（自动管理）。Flow 用协程 scope 自动取消，天然不易泄漏。`

### 问题8：Cold Observable 和 Hot Observable 的区别？

**答案要点**：
- **Cold（冷）**：每次订阅都从头发射数据，每个订阅者独立数据流
  - 类比：点播视频（每个人从头看）
  - 例子：Observable.create、Observable.just、Kotlin Flow
- **Hot（热）**：不管有没有订阅者都在发射数据，订阅者只能收到订阅后的数据
  - 类比：直播（你加入后只能看到之后的内容）
  - 例子：PublishSubject、SharedFlow
- BehaviorSubject/StateFlow：热流但保留最新值，新订阅者立刻收到最新值
- 冷转热：share()（RxJava）、shareIn()（Flow）

**记忆要点**：`冷=点播（每人独立），热=直播（共享一条流）。Cold Observable 懒执行，Hot Observable 立刻执行。StateFlow/BehaviorSubject 是"回放最新一条的直播"。`
