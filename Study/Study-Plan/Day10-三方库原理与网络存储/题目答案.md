## 口述题

#### 1. 画出 OkHttp 拦截器链的完整流程图，说明每个拦截器做什么（口述题）
**要点：**
- 用户自定义拦截器 → 重试拦截器 → 桥接拦截器 → 缓存拦截器 → 连接拦截器 → 网络拦截器 → CallServer 拦截器。
- 每层职责：
  - RetryAndFollowUpInterceptor：处理失败重试、重定向。
  - BridgeInterceptor：补充请求头（User-Agent、Host、Cookie）。
  - CacheInterceptor：读写缓存策略（针对 GET）。
  - ConnectInterceptor：建立/复用连接。
  - NetworkInterceptor：链路层面拦截（只能操作网络请求）。
  - CallServerInterceptor：真正写入/读取 socket。

**解析：**
链条本质是责任链模式：每个拦截器通过 `chain.proceed(request)` 交棒。了解顺序可帮助定位是缓存命中还是网络请求发出，以及某拦截器抛出的异常。

#### 2. Glide 加载一张图片的完整流程（从 URL 到显示在 ImageView 上）（口述题）
**要点：**
- RequestBuilder 构建请求 → EngineKey 确定缓存 Key → 内存缓存命中？→ 资源缓存？→ 数据缓存？→ ModelLoader 拉取数据 → 解码 → Transcoder → Target 回调。
- 四级缓存：Active Resources、MemoryCache、Resource Disk Cache、Data Disk Cache。
- 生命周期绑定：通过 RequestManager（空 Fragment）监听 onStart/onStop。

**解析：**
Glide 发起请求后先在 Active Resources 和 LruResourceCache 查找。未命中则检查磁盘缓存：Resource（解码后的一致格式）和 Data（原始数据）。都 miss 时通过 ModelLoader（如 HttpUrlFetcher）拉取数据，解码成 Bitmap/GifDrawable，最后交给 Target 并放入缓存。整个流程通过线程池调度，且 RequestManager 跟随生命周期，避免内存泄漏。

#### 3. TCP 三次握手和四次挥手的过程，为什么握手三次挥手四次？（口述题）
**要点：**
- 三次握手：SYN → SYN+ACK → ACK，确保双方都能收发。
- 四次挥手：FIN → ACK → FIN → ACK，因为关闭连接是双向的，发送端和接收端需要各自确认。
- TIME_WAIT 防止旧包影响新连接。

**解析：**
握手过程中第三次 ACK 确保客户端知道服务器的 SYN/ACK 已送达；挥手时，主机需要先确认对方的 FIN，再等待自己数据发送完毕后发送 FIN，最后对方 ACK。这样保证数据不丢失。TIME_WAIT 通常持续 2MSL，以防迟到的包。

## 场景分析题

#### 4. 你的 App 在弱网环境下请求超时严重，如何优化？列出至少 4 个方案和依据（场景分析题）
**要点：**
- 启用 `Call.timeout` + `retryOnConnectionFailure`，自定义重试策略。
- 使用链路探测/预连接，提前建立 TCP/TLS。
- 启用压缩、合并接口、分页加载。
- 配置多域名/HTTPDNS、TLS False Start。

**解析：**
具体方案：1) 针对超时类型（连接/读写）设置差异化超时；2) 使用 `OkHttpClient.Builder.dns()` 加入 HTTPDNS 提高解析速度；3) 缓存静态数据（Etag/If-None-Match）；4) 在弱网检测到高延迟时降级图片质量或减少请求量。

#### 5. SP 在什么情况下会导致 ANR？如何迁移到 DataStore/MMKV？（场景分析题）
**要点：**
- `SharedPreferences.apply()` 在写入文件时仍可能在主线程等待，尤其在多进程或频繁提交时。
- 大量 XML 序列化会阻塞 UI，触发 Input ANR。
- 迁移到 DataStore（基于 Flow+Coroutines）或 MMKV（mmap）可异步写入。

**解析：**
SP 文件越大写入越慢，且 XML 解析在主线程完成。迁移策略：使用 DataStore Preferences/Proto 将读取写入放在协程；或使用 MMKV，将数据映射到内存，写入落盘由 mmap 托管，并支持多进程模式。

## 代码题

#### 6. 写一个 OkHttp 拦截器，实现：统一添加 Token + 401 时自动刷新 Token 重试（代码题）
**要点：**
- 在 `intercept` 中为每个请求添加最新 Token 头。
- 遇到 401 时调用刷新接口（阻塞或同步）获取新 Token，再重试一次。
- 需要防止并发刷新：可使用 `synchronized` 或 `Mutex`。

**解析：**
示例使用 Kotlin，刷新逻辑通过 `TokenRepository.refresh()` 实现。重试次数受限，避免死循环。

**示例代码：**
```kotlin
class AuthInterceptor(
    private val tokenRepo: TokenRepository
) : Interceptor {

    override fun intercept(chain: Interceptor.Chain): Response {
        var request = attachToken(chain.request())
        var response = chain.proceed(request)

        if (response.code == 401) {
            response.close()
            synchronized(this) {
                if (tokenRepo.isTokenExpired()) {
                    tokenRepo.refresh()
                }
            }
            request = attachToken(chain.request())
            response = chain.proceed(request)
        }
        return response
    }

    private fun attachToken(request: Request): Request {
        val token = tokenRepo.getToken()
        return request.newBuilder()
            .header("Authorization", "Bearer $token")
            .build()
    }
}

interface TokenRepository {
    fun getToken(): String
    fun isTokenExpired(): Boolean
    fun refresh()
}

class MemoryTokenRepository : TokenRepository {
    @Volatile private var token: String = "initial"
    @Volatile private var expired: Boolean = false

    override fun getToken(): String = token

    override fun isTokenExpired(): Boolean = expired

    override fun refresh() {
        // 发起同步刷新接口
        val newToken = "token_${System.currentTimeMillis()}"
        token = newToken
        expired = false
    }

    fun markExpired() { expired = true }
}

fun createClient(): OkHttpClient {
    val repo = MemoryTokenRepository()
    return OkHttpClient.Builder()
        .addInterceptor(AuthInterceptor(repo))
        .build()
}
```

**说明：**
真实项目中刷新接口需要阻塞执行或用 `runBlocking` 确保刷新完成。可将 Token 存储在 DataStore/MMKV，并在刷新成功后广播，使其他请求能复用。
