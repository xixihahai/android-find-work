## 口述题

#### 1. 画出 JVM 内存区域图，说出每个区域存什么、哪些是线程共享的（口述题）
**要点：**
- JVM 运行时划分为方法区、堆、程序计数器、Java 虚拟机栈、本地方法栈。
- 方法区与堆为线程共享，存放类型信息、常量、静态变量和对象实例。
- 程序计数器、Java 栈、本地方法栈为线程私有，存放执行位置、栈帧和 native 调用状态。

**解析：**
方法区（JDK 8 起为元空间）承担类元数据、常量池、JIT 生成代码，易出现 `OutOfMemoryError: Metaspace`。堆是 GC 管理的最大区域，存放对象实例及其成员，受 `-Xms/-Xmx` 控制。程序计数器是字节码执行行号寄存器，保证线程切换后能恢复。Java 虚拟机栈由多个栈帧组成，每个栈帧含局部变量表、操作数栈、动态链接和方法退出信息。native 方法通过本地方法栈与 JNI 交互。判断线程共享与否可结合是否需要加锁以及是否有 GC 管理：共享区域是 GC 关注重点，私有区域导致的 OOM 通常表现为 `StackOverflowError` 或 `OutOfMemoryError: unable to create new native thread`。

#### 2. 描述 HashMap.put() 的完整流程（包括扩容和红黑树转换条件）（口述题）
**要点：**
- 计算 key 的哈希并定位桶位，若桶为空直接插入节点。
- 桶内存在节点时比较 key：命中则覆盖，未命中则在链尾追加或在树中插入。
- 节点数量超过 `threshold=loadFactor*capacity` 时触发扩容；链表长度 ≥ 8 且容量 ≥ 64 时树化。

**解析：**
JDK 8 的 `hash()` 会做高 16 位异或，降低碰撞。定位桶位后若命中 `TreeNode` 则调用 `putTreeVal`，否则遍历链表，若到末尾仍未找到则新建节点并挂在末尾（同时记录链长）。插入结束后若链长 ≥ 8 会尝试树化，但需要表容量达到 64；否则通过 `resize()` 将数组容量翻倍并重新分布，把链表拆分到新桶。扩容过程中节点根据原索引和新索引 `i`、`i+oldCap` 拆分，可避免重新计算 hash。树转回链表发生在删除元素后链长 < 6 的情况。

#### 3. 解释 ConcurrentHashMap 在 JDK 1.7 和 1.8 的区别（口述题）
**要点：**
- JDK 7 采用 Segment（分段锁），每段本质是一个小 HashMap。
- JDK 8 改用 Node 数组 + CAS + `synchronized`，不再分段，桶内可能树化。
- 1.8 支持无锁插入（CAS 设置桶头）和协作扩容，提高并发度。

**解析：**
JDK 7 的 `ConcurrentHashMap` 预先创建 16 个 Segment，每段维护自己的 `HashEntry[]` 和锁，读操作无锁，写操作锁住对应 Segment，但 Segment 数固定时高并发仍会争用。JDK 8 取消 Segment，统一使用 `Node[] table`，通过 `Unsafe` 的 CAS 设置首节点，若 CAS 失败再退化为 `synchronized` 自旋。扩容采用 `ForwardingNode` 标记，多个线程可以分配桶区间协作迁移。桶内元素过多时也会树化（`TreeBin`），并提供 `CounterCell` 分布式计数避免全局锁。整体提升吞吐并降低内存浪费。

## 场景分析题

#### 4. 你的 App 出现了频繁 GC（内存锯齿），可能是什么原因？从 JVM 角度分析（场景分析题）
**要点：**
- 新生代 Eden 区频繁被填满，导致 Minor GC 连续触发。
- Survivor 容量不足导致对象提前晋升老年代，引发 Full GC。
- 短生命周期对象在主线程密集创建，伴随内存抖动。

**解析：**
JVM 默认采用分代收集，短命对象进入新生代。若应用频繁分配大对象或一次性创建大量集合（例如解析 JSON、Bitmap decode），会迅速耗尽 Eden。未能及时回收的对象会在 Survivor 区复制多次，Survivor 不足时提前晋升老年代，老年代满又会触发 Full GC。针对 Android，需配合 `Android Studio Profiler` 和 `adb shell dumpsys meminfo` 分析对象分配热点，采用对象池、复用 Buffer、延迟加载等策略，并调优线程池/缓存策略减少抖动。还需检查是否存在缓存未命中导致重复创建、或 `Bitmap`/`Drawable` 未及时回收的情况。

#### 5. Android 的 ArrayMap 和 HashMap 有什么区别？什么场景用哪个？为什么？（场景分析题）
**要点：**
- ArrayMap 基于排序数组（折半查找）+ 内联存储，内存占用更小，适合几十个元素以内。
- HashMap 基于哈希桶，插入/查询平均 O(1)，更适合元素数量大或频繁扩容场景。
- ArrayMap 不线程安全，迭代顺序稳定；HashMap 需要注意扩容和迭代期间结构变化。

**解析：**
`ArrayMap` 在 Android Support 库中使用两个数组存储哈希和值，避免为每个节点分配对象，减少 GC 压力。但插入和删除需要移动数组，复杂度 O(n)，适合 `Bundle`、`Fragment` 参数等小集合。`HashMap` 需要额外 Node 包装，内存开销更大但查找 O(1)。在性能优化中可使用 `ArrayMap` 替换小型 `HashMap`，但在多线程或元素数量级达到数百时仍应选择 `HashMap` 或 `ConcurrentHashMap`。另外 `SparseArray` 系列可以替换 `HashMap<Integer, Object>`，进一步省内存。

## 代码题

#### 6. 手写一个线程安全的 LRU 缓存（基于 LinkedHashMap），说明为什么用 LinkedHashMap（代码题）
**要点：**
- 继承 `LinkedHashMap` 并启用 accessOrder，即可在 `removeEldestEntry` 中淘汰最旧条目。
- 用 `ReentrantLock` 或 `synchronized` 保护并发访问，保证线程安全。
- 提供 `put/get`/`size` 方法和简单示例以验证淘汰策略。

**解析：**
`LinkedHashMap` 维护双向链表，可选择访问顺序，天然适合 LRU。通过覆盖 `removeEldestEntry` 可自动驱逐最老节点。为了线程安全，可以在外层使用 `ReentrantLock` 包裹所有写操作，并在 `get` 时同样加锁以维护访问顺序。示例中演示容量溢出时最早访问的键被移除。

**示例代码：**
```java
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.concurrent.locks.ReentrantLock;

public class SafeLruCache<K, V> {
    private final ReentrantLock lock = new ReentrantLock();
    private final LinkedHashMap<K, V> cache;

    public SafeLruCache(final int maxSize) {
        this.cache = new LinkedHashMap<K, V>(maxSize, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
                return size() > maxSize;
            }
        };
    }

    public void put(K key, V value) {
        lock.lock();
        try {
            cache.put(key, value);
        } finally {
            lock.unlock();
        }
    }

    public V get(K key) {
        lock.lock();
        try {
            return cache.get(key);
        } finally {
            lock.unlock();
        }
    }

    public int size() {
        lock.lock();
        try {
            return cache.size();
        } finally {
            lock.unlock();
        }
    }

    public static void main(String[] args) {
        SafeLruCache<Integer, String> lru = new SafeLruCache<>(2);
        lru.put(1, "A");
        lru.put(2, "B");
        lru.get(1); // 访问 1，使其变为最近使用
        lru.put(3, "C"); // 淘汰 key 2
        System.out.println(lru.get(1)); // 输出 A
        System.out.println(lru.get(2)); // 输出 null
        System.out.println(lru.get(3)); // 输出 C
    }
}
```

**说明：**
通过 access-order 的 `LinkedHashMap` 我们无需维护额外链表，淘汰规则集中在 `removeEldestEntry`。示例展示了最近被访问的键不会被淘汰的特性。在生产环境中可以进一步封装统计指标或改用 `ReadWriteLock` 以提升并发读性能。
