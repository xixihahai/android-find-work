## 口述题

#### 1. suspend 函数编译后的代码是什么样的？画出状态机的状态转换（口述题）
**要点：**
- Kotlin 编译器将 `suspend` 函数转换成接收额外 `Continuation` 参数的普通函数。
- 函数体被拆成状态机（`label` 字段指示执行节点），每次挂起保存局部变量到 `Continuation`。
- 恢复时根据 `label` 决定跳转到具体状态。

**解析：**
以 `suspend fun foo()` 为例，反编译后生成 `Object foo(Continuation cont)`，并创建 `Foo$foo$1` 继承 `ContinuationImpl`。挂起点（例如 `delay`）前会写入 `label=1`、保存局部变量，返回 `COROUTINE_SUSPENDED`。当协程被恢复时，`resumeWith` 调用内部 `invokeSuspend`，通过 `switch(label)` 跳到对应 case。状态机确保协程可以在任意挂起点暂停/恢复，同时生成的类持有 `completion` 引用以便向上层汇报结果。

#### 2. StateFlow 和 SharedFlow 的区别，分别适用什么场景？（口述题）
**要点：**
- StateFlow 是冷到热的桥梁，必须有初始值，只存储最新状态，具备粘性、可重复收集。
- SharedFlow 是多播热流，可配置 `replay`、缓冲和丢弃策略，支持无初始值。
- UI 状态 -> StateFlow；事件流/总线 -> SharedFlow。

**解析：**
StateFlow 实现 `StateFlowImpl`，内部维护单值数组；`collect` 时立即发送当前值，实现“最新状态可见”。SharedFlow (`SharedFlowImpl`) 则维护环形缓冲及多个订阅者索引，可配置 `replay`（粘性事件）和 `extraBufferCapacity`（背压）。StateFlow 只支持 conflated 模式且永不完成，适合 `ViewState`、`FormState`；SharedFlow 可以完成或无初始值，适合导航事件、一次性 Toast。选择依据为“状态 vs 事件”和是否需要重放/缓冲。

#### 3. `by lazy` 的线程安全是如何实现的？有哪几种模式？（口述题）
**要点：**
- Kotlin 提供 `LazyThreadSafetyMode.SYNCHRONIZED`（默认）、`PUBLICATION`、`NONE`。
- 默认模式使用 `synchronized` + 双重检查，保证只初始化一次。
- `PUBLICATION` 允许多线程并发初始化但最终只保留一个结果；`NONE` 不加锁，仅适合单线程。

**解析：**
`SYNCHRONIZED` 模式内部使用对象锁并在第二次进入时直接返回缓存值。`PUBLICATION` 通过原子引用保存初始化结果，多个线程可能同时执行初始化 lambda，但最终 CAS 设置一次，其余结果被丢弃。`NONE` 不加锁，性能最好但若在多线程访问将可能重复初始化。选择时遵循“是否多线程访问 + 初始化成本是否昂贵”。

## 场景分析题

#### 4. 在 ViewModel 中应该用 `LiveData` 还是 `StateFlow`？说出你的选择和依据（场景分析题）
**要点：**
- 对需要保存 UI 状态且支持重放最新值的场景推荐 StateFlow。
- StateFlow 原生支持协程作用域和背压，不会出现粘性事件问题。
- 若已有大量 LiveData 观察者且依赖其生命周期感知，可混用并逐步迁移。

**解析：**
ViewModelScope 默认运行在 `Dispatchers.Main.immediate`，StateFlow 与协程天然配合，可以使用 `stateIn` 将仓库流转换为 UI 状态，并利用 `update` 保证原子修改。LiveData 虽具备生命周期感知，但缺少背压/变换能力，且粘性事件需要额外封装。一种折中方案是仓库层使用 Flow，UI 侧根据需要转换成 LiveData (`asLiveData`)。最终目标是统一到 StateFlow/SharedFlow 提升一致性。

#### 5. 一个搜索框需要实现防抖（用户停止输入 300ms 后才发请求），用 Flow 怎么实现？为什么用 Flow 而不是 Handler.postDelayed？（场景分析题）
**要点：**
- 使用 `callbackFlow` 或 `MutableStateFlow` 收集输入，然后 `debounce(300)` + `distinctUntilChanged()`。
- Flow 防抖天然与协程作用域绑定，可在测试中轻松调度。
- 相比 Handler，Flow 支持背压、取消、组合运算符，逻辑更可组合。

**解析：**
`textChanges()` -> `.debounce(300)` -> `.filter { it.isNotBlank() }` -> `.onEach { query -> search(query) }`. 当视图销毁时协程自动取消，避免 Handler 延迟消息泄漏。Flow 的可组合操作符使得后续可以直接链式加入 `mapLatest`、`retryWhen`，而 Handler 需要手写状态机且难以测试。

## 代码题

#### 6. 用 Flow 实现一个简单的 EventBus（支持粘性事件和非粘性事件）（代码题）
**要点：**
- SharedFlow 通过 `replay` 支持粘性事件，`extraBufferCapacity` 与 `onBufferOverflow` 控制非粘性模式。
- 提供 `postSticky`, `post`, `observeSticky`, `observe` 等 API。
- 结合 `CoroutineScope` 在示例中展示跨组件事件分发。

**解析：**
SharedFlow 是多播热流，非常适合事件总线。粘性事件需求可以设置 `replay = 1` 并在 `postSticky` 前清空或替换；非粘性事件则使用 `replay = 0` 并允许缓冲一个 slot。示例在 `main` 中使用 `runBlocking` 演示订阅。

**示例代码：**
```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.MutableSharedFlow
import kotlinx.coroutines.flow.collect

object FlowBus {
    private val stickyFlow = MutableSharedFlow<Any>(replay = 1)
    private val normalFlow = MutableSharedFlow<Any>(replay = 0, extraBufferCapacity = 16)

    suspend fun post(event: Any) {
        normalFlow.emit(event)
    }

    suspend fun postSticky(event: Any) {
        stickyFlow.emit(event)
    }

    fun observe(scope: CoroutineScope, onEvent: (Any) -> Unit) {
        scope.launch { normalFlow.collect { onEvent(it) } }
    }

    fun observeSticky(scope: CoroutineScope, onEvent: (Any) -> Unit) {
        scope.launch { stickyFlow.collect { onEvent(it) } }
    }
}

fun main() = runBlocking {
    val job = CoroutineScope(Dispatchers.Default).launch {
        FlowBus.observeSticky(this) { println("Sticky -> $it") }
    }
    FlowBus.postSticky("AppReady")
    FlowBus.post("NewMessage")
    FlowBus.observe(this) { println("Normal -> $it") }
    FlowBus.post("AnotherMessage")
    delay(200)
    job.cancel()
}
```

**说明：**
`observeSticky` 在订阅瞬间就能收到最后一次 `postSticky` 的事件，`observe` 只处理订阅之后的新事件。生产环境可为不同事件定义类型安全封装（sealed class）并加入 `CoroutineScope` 生命周期管理。
