## 口述题

#### 1. 从按下电源键到看到 Launcher 界面，经历了哪些关键步骤？（口述题）
**要点：**
- BootROM → Bootloader → Kernel → init 进程 → Zygote → SystemServer → 启动 Launcher。
- init 读取 `init.rc` 启动 zygote / servicemanager / logd 等守护进程。
- SystemServer 启动 AMS/WMS/PMS，最后通过 AMS 启动 Launcher。

**解析：**
BootROM 在芯片上电后执行，加载 Bootloader（二级/三级）。Bootloader 初始化硬件、加载 Linux 内核。Kernel 启动后创建第一个用户态进程 `init`，解析 rc 脚本启动 Zygote。Zygote 预加载类和资源，监听 socket 等待 AMS 请求 fork App 进程。SystemServer 作为 Zygote fork 的首个进程，启动 AMS/WMS/PMS 等服务，再向 AMS 发起启动 Launcher Intent。

#### 2. 为什么所有 App 进程都是 Zygote fork 出来的？这样设计的好处？（口述题）
**要点：**
- fork 能复制父进程已预加载的类、资源和 JIT 结果，减少启动时间。
- 共享只读页（COW）节省内存。
- 统一入口便于 AMS 管理进程生命周期和优先级。

**解析：**
Zygote 预加载 framework 类和资源，fork 子进程时通过写时复制技术共享内存页，大幅缩短冷启动。AMS 通过 socket 指令控制 Zygote fork，确保每个进程都遵守统一安全策略，如 SELinux 上下文和 Nice 值。

#### 3. startActivity 从 App 进程到 system_server 进程再回到 App 进程的完整流程（口述题）
**要点：**
- 客户端 `Instrumentation.execStartActivity` 通过 Binder 调用 AMS (`IActivityTaskManager`)。
- AMS 校验 Intent/权限，选择目标任务栈并调度 ActivityRecord。
- AMS 指示目标进程（若未启动则通过 Zygote fork）执行 `scheduleLaunchActivity`，ActivityThread 创建 Activity。

**解析：**
App 进程调用 `ActivityTaskManagerService.startActivityAsUser`，system_server 侧完成栈管理、进程调度，必要时调用 `ProcessList.startProcessLocked()` 通过 Zygote fork 新进程。随后 AMS 通过 Binder 回调到目标进程的 `IApplicationThread.scheduleLaunchActivity`，ActivityThread 收到消息后创建 Activity、调用生命周期。

## 场景分析题

#### 4. 一个 App 在后台被系统杀死了，用户从最近任务点击回来后发生了什么？AMS 做了什么？（场景分析题）
**要点：**
- 最近任务记录 Task 信息；点击时 AMS 检查目标进程是否存在，不存在则重新 fork。
- AMS 将任务放回前台，并向 `ActivityThread` 发送 `scheduleCreateActivity`。
- 若 Activity 有 `savedInstanceState`，会在 `onCreate`/`onRestoreInstanceState` 恢复 UI。

**解析：**
当进程被 LMK 杀死后，任务记录仍在 AMS 中。用户点击卡片后，AMS 通过 `ProcessList.startProcessLocked()` 启动进程，并把 `Intent`/`ActivityOptions` 传给新进程，表现类似冷启动但任务栈 ID 保持不变。开发者需在 `onSaveInstanceState` 保存 UI 状态，避免“白屏”。

#### 5. 为什么 Android 11+ 你的 App 查不到其他 App 的信息了？PMS 做了什么变化？（场景分析题）
**要点：**
- Android 11 引入 `package visibility`，默认只能看到声明的 package。
- PMS 根据 `queries` 清单、`PackageManager.MATCH_*` flag 判定是否返回目标包信息。
- 需要在 manifest 中声明 `<queries>` 或使用 `PackageManager#getInstalledPackages(PackageManager.MATCH_ALL)` 搭配权限。

**解析：**
为保护隐私，Android 11 限制应用枚举已安装 App。PMS 在处理 `queryIntentActivities`、`getInstalledPackages` 等 API 时，会根据调用方 UID 和 `queries` 规则过滤结果。未声明的包将被隐藏，返回空列表或抛异常。解决方案是在 `AndroidManifest` 的 `<queries>` 节点列出需要访问的包名、IntentAction，或请求 `QUERY_ALL_PACKAGES` 权限（仅限特定用途）。

## 代码题

#### 6. 写一段代码获取当前 App 的所有 Activity（通过 PackageManager），说明用到了 PMS 的哪个功能（代码题）
**要点：**
- 使用 `PackageManager.getPackageInfo(packageName, GET_ACTIVITIES)`。
- 遍历 `PackageInfo.activities` 输出组件名。
- 需要处理 `PackageManager.NameNotFoundException`。

**解析：**
PMS 负责解析 APK 并维护四大组件信息。通过 `PackageManager` 可以查询当前包里声明的 Activity，以便调试或生成路由表。

**示例代码：**
```java
public class ActivityInspector {
    public static List<String> listDeclaredActivities(Context context) {
        PackageManager pm = context.getPackageManager();
        try {
            PackageInfo info = pm.getPackageInfo(
                    context.getPackageName(),
                    PackageManager.GET_ACTIVITIES
            );
            List<String> result = new ArrayList<>();
            if (info.activities != null) {
                for (ActivityInfo activityInfo : info.activities) {
                    result.add(activityInfo.name);
                }
            }
            return result;
        } catch (PackageManager.NameNotFoundException e) {
            throw new IllegalStateException(e);
        }
    }

    public static void main(String[] args) {
        // 在 Android 中可放到 Application.onCreate 里打印
        // 这里仅展示调用方式
    }
}
```

**说明：**
调用 `GET_ACTIVITIES` 就是 PMS 提供的元数据查询能力。若希望运行时列出可启动 Activity，还可结合 `PackageManager.queryIntentActivities`。
