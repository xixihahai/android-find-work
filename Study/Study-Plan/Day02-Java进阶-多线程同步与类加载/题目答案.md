## 口述题

#### 1. synchronized 的锁升级过程，为什么要设计锁升级而不是直接用重量级锁？（口述题）
**要点：**
- 偏向锁：无竞争场景下只记录线程 ID，几乎零开销。
- 轻量级锁：存在竞争时通过 CAS 自旋获取锁，避免内核态互斥。
- 重量级锁：竞争激烈时挂起/唤醒线程，防止自旋浪费 CPU。

**解析：**
对象头包含 Mark Word，可在偏向锁状态记录持有线程和时间戳；若检测到竞争（例如其他线程尝试获取锁），会撤销偏向锁并升级为轻量级锁，使用自旋 + CAS 修改锁记录。自旋次数超过阈值或线程被阻塞时，再膨胀为重量级锁（Monitor），依赖 OS Mutex。这样的层级允许 JVM 根据竞争程度动态权衡吞吐与响应：大量单线程或无竞争代码路径享受偏向锁带来的低开销，而在高竞争场景下又能保证公平和稳定。

#### 2. 解释双亲委派机制，以及 Android 热修复如何打破双亲委派（口述题）
**要点：**
- ClassLoader 加载类前先委派给父加载器，避免重复加载和安全冲突。
- 热修复通过自定义 ClassLoader 或调整 DexElements 顺序，让补丁 Dex 在系统 Dex 前被搜索。
- 也可通过替换字段（如 `BaseDexClassLoader.pathList.dexElements`）实现“先补丁后系统”。

**解析：**
双亲委派保证了 Java 核心类由 Bootstrap/PathClassLoader 统一加载，防止应用自定义 `java.lang.String`，提升安全。Android 热修复方案（Tinker、AndFix 等）通过自定义 `DexClassLoader` 把补丁 Dex 插到原始 `DexPathList` 前面，或在 `ApplicationLike` 中反射修改 `dexElements`，使得类解析时优先命中补丁版本，从而绕过父类加载器优先级。由于补丁只影响特定包名，不会破坏系统类，且加载流程仍复用现有 ClassLoader。

#### 3. 为什么 `List<String>` 和 `List<Integer>` 在运行时是同一个类型？有什么影响？（口述题）
**要点：**
- Java 泛型采用擦除实现，编译后统一转成原始类型 `List`，类型参数以桥接方法/`Signature` 保留。
- 运行时无法区分不同参数化类型，导致无法重载或直接获取 `T` 的 Class。
- 需要借助 `TypeToken`、`ParameterizedType` 或在构造函数中传入 `Class<T>`。

**解析：**
擦除让 JVM 保持向后兼容：泛型信息主要用于编译期类型检查。编译器会在必要处插入 `checkcast`。由于运行时只看到 `List`，因此 `instanceof List<String>` 不合法；反射 API (`getGenericSuperclass`) 只能在类或字段上获取泛型形参。像 Retrofit 解析接口返回类型时，需要通过 `ParameterizedTypeImpl` 读取方法签名并提取实际类型。开发中若直接使用 raw type 会丢失类型安全。

## 场景分析题

#### 4. 单例模式中的 DCL（Double Check Lock）为什么需要 volatile？不加会怎样？（场景分析题）
**要点：**
- `volatile` 既保证可见性也禁止指令重排序。
- 没有 `volatile` 时，构造函数可能与引用赋值重排序，导致其他线程拿到未初始化对象。
- DCL 的两个判空可降低锁竞争，但依赖 `volatile` 才能安全。

**解析：**
DCL 创建步骤包含：1) 分配内存；2) 调用构造函数；3) 将引用赋值给静态变量。编译器或 CPU 可能重排序 2、3，使得引用先可见，另一个线程通过第一次判空获得半初始化对象并访问成员导致崩溃。`volatile` 在写入时会插入 StoreStore/StoreLoad 屏障，确保构造完成后才发布引用，也使得读到的引用对所有线程可见。替代方案还有静态内部类或 `enum`，但当必须用 DCL 时务必加 `volatile`。

#### 5. Retrofit 是如何在运行时获取接口方法的泛型返回类型的？（场景分析题）
**要点：**
- Retrofit 在 `ServiceMethod` 构建阶段通过反射读取 `Method` 的 `getGenericReturnType()`。
- 结合 `callAdapterFactory`/`converterFactory`，解析 `ParameterizedType` 并提取 `T`。
- 解析结果缓存，避免重复处理。

**解析：**
当你调用 `Retrofit.create(Api.class)` 时，Retrofit 使用动态代理捕获接口方法。第一次调用某方法时，会创建 `ServiceMethod`，期间通过 `Utils.getParameterUpperBound()` 等工具解析 `Call<ResponseBody>`、`Call<ApiResponse<User>>` 等嵌套类型。若返回类型是 `Call<T>`，则取出 `T` 交给对应的 `ConverterFactory`。该流程依赖泛型签名保留在方法元数据中，因此 Retrofit 不需要运行时保留泛型对象即可推断类型。

## 代码题

#### 6. 实现一个 TypeToken 类，能在运行时获取泛型类型参数（代码题）
**要点：**
- 通过创建匿名子类捕获泛型信息，如 `new TypeToken<List<String>>() {}`。
- 在父类构造函数内读取 `getGenericSuperclass()` 并解析 `ParameterizedType`。
- 提供 `getType()`、`getRawType()` 等方法便于上层框架使用。

**解析：**
思路参考 Gson 的 `TypeToken`：由于 Java 擦除导致普通实例获取不到 `T`，但匿名子类在字节码中会把实际类型写入 `Signature`。在抽象父类构造函数读取该签名即可解析。实现时需要处理 `Class`、`ParameterizedType`、`GenericArrayType` 等情况。示例提供基本能力，可拓展支持 `equals/hashCode` 以便作为 Map key。

**示例代码：**
```java
import java.lang.reflect.ParameterizedType;
import java.lang.reflect.Type;

public abstract class TypeToken<T> {
    private final Type type;

    protected TypeToken() {
        Type superType = getClass().getGenericSuperclass();
        if (superType instanceof Class) {
            throw new IllegalArgumentException("TypeToken must be created with generic type.");
        }
        this.type = ((ParameterizedType) superType).getActualTypeArguments()[0];
    }

    public Type getType() {
        return type;
    }

    public Class<?> getRawType() {
        if (type instanceof Class<?>) {
            return (Class<?>) type;
        }
        if (type instanceof ParameterizedType) {
            return (Class<?>) ((ParameterizedType) type).getRawType();
        }
        throw new IllegalStateException("Unsupported type: " + type);
    }

    public static void main(String[] args) {
        TypeToken<java.util.List<String>> token = new TypeToken<java.util.List<String>>() {};
        System.out.println("Type: " + token.getType());
        System.out.println("RawType: " + token.getRawType());
    }
}
```

**说明：**
运行示例可打印 `java.util.List<java.lang.String>`，表明泛型被捕获。Retrofit/Gson 等库会基于该 Type 决定解析逻辑。生产可扩展支持 `TypeUtils.canonicalize` 以处理数组、通配符。
