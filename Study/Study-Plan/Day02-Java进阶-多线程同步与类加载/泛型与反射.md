# 泛型与反射

## 速记总结

### 一句话理解
> 泛型就像模具——编译时约束类型安全，运行时模具被拆掉(类型擦除)。反射就像X光——运行时可以透视类的内部结构。

### 核心知识点速记
| 知识点 | 一句话记忆 | 面试频率 |
|--------|-----------|---------|
| 类型擦除 | 编译后泛型变Object/上界，运行时无泛型信息 | ★★★★★ |
| 通配符 | ? extends(上界,只读) vs ? super(下界,只写) → PECS原则 | ★★★★☆ |
| 获取泛型信息 | 匿名内部类/TypeToken保留泛型签名(Signature属性) | ★★★★☆ |
| 反射获取类信息 | Class.forName/getClass/.class三种方式 | ★★★★☆ |
| 反射性能 | 比直接调用慢,可通过setAccessible(true)和缓存优化 | ★★★☆☆ |
| Kotlin reified | 内联函数+reified保留泛型类型,避免传Class参数 | ★★★★☆ |
| 注解+反射 | 运行时注解通过反射读取,编译时注解用APT处理 | ★★★★☆ |

### 与其他知识的串联
- **类型擦除 → Gson/Retrofit泛型解析**：Gson用TypeToken获取泛型类型，Retrofit通过方法签名的泛型信息解析返回类型
- **反射 → Retrofit动态代理**：Retrofit用Proxy.newProxyInstance拦截接口方法调用，反射获取注解和泛型信息
- **反射 vs APT → 性能权衡**：运行时反射有性能开销，ButterKnife/Dagger用APT编译时生成代码替代反射(更优方案)

---

## 1. 概述

泛型和反射是 Java 语言的两个重要特性。泛型提供了编译时类型安全检查，反射则允许程序在运行时检查和操作类的结构。本文将深入讲解泛型的类型擦除机制、通配符使用，以及反射的原理和性能优化。

### 2.2 类型擦除

```

├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  什么是类型擦除:                                                        │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  Java 泛型是伪泛型，只在编译期有效                              │   │

│  │  List<T>               │  List                                  │   │
│  │  T                     │  Object                                │   │

│  │      public void setValue(T value) { this.value = value; }      │   │
```

### 2.3 通配符

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          通配符 (Wildcards)                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  三种通配符:                                                            │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  1. 无界通配符: <?>                                             │   │
│  │  2. 上界通配符: <? extends T>  (协变)                           │   │
│  │  3. 下界通配符: <? super T>    (逆变)                           │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  类型继承关系:                                                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │                        Object                                   │   │
│  │                           ↑                                     │   │
│  │                        Number                                   │   │
│  │                       ↗      ↖                                  │   │
│  │                  Integer    Double                              │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  上界通配符 <? extends Number>:                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  - 可以接受 Number 及其子类                                     │   │
│  │  - 只能读取 (生产者)，不能写入                                  │   │
│  │                                                                 │   │
│  │  List<? extends Number> list;                                   │   │
│  │  Number n = list.get(0);  // ✓ 可以读取为 Number               │   │
│  │  list.add(1);             // ✗ 编译错误，不能写入               │   │
│  │                                                                 │   │
│  │  原因: 编译器不知道具体类型，可能是 List<Integer> 或 List<Double>│   │
│  │        如果允许写入，可能导致类型不匹配                         │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  下界通配符 <? super Integer>:                                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  - 可以接受 Integer 及其父类                                    │   │
│  │  - 只能写入 (消费者)，读取只能是 Object                         │   │
│  │                                                                 │   │
│  │  List<? super Integer> list;                                    │   │
│  │  list.add(1);             // ✓ 可以写入 Integer                │   │
│  │  Object o = list.get(0);  // ✓ 只能读取为 Object               │   │
│  │  Integer i = list.get(0); // ✗ 编译错误                        │   │
│  │                                                                 │   │
│  │  原因: 编译器不知道具体类型，可能是 List<Integer>、List<Number>  │   │
│  │        或 List<Object>，只能确定可以写入 Integer                │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  PECS 原则 (Producer Extends, Consumer Super):                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  - 如果只读取数据 (生产者)，使用 <? extends T>                  │   │
│  │  - 如果只写入数据 (消费者)，使用 <? super T>                    │   │
│  │  - 如果既读又写，不使用通配符                                   │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 3. 关键源码解析

### 3.1 泛型类型擦除示例

```java
/**
 * 泛型类型擦除 —— 编译前后对比
 *
 * 核心要点：Java 泛型只在编译期存在，编译后所有泛型信息都被擦除。
 * 编译器会自动插入必要的类型转换（checkcast 指令），以保证运行时类型安全。
 */

// ==================== 编译前 (源码) ====================

public class Box<T> {
    private T value;

    public void setValue(T value) {
        this.value = value;
    }

    public T getValue() {
        return value;
    }
}

// 使用处
Box<String> box = new Box<>();
box.setValue("hello");
String s = box.getValue();  // 无需手动强转


// ==================== 编译后 (字节码等价 Java 代码) ====================

public class Box {
    private Object value;  // T → Object

    public void setValue(Object value) {  // T → Object
        this.value = value;
    }

    public Object getValue() {  // T → Object
        return value;
    }
}

// 使用处（编译器自动插入 checkcast）
Box box = new Box();
box.setValue("hello");
String s = (String) box.getValue();  // 编译器插入强制类型转换
```

### 3.2 反射获取泛型信息（ParameterizedType）

```java
/**
 * 虽然类型擦除会在运行时删除泛型信息，但 Java 在 **类的元数据** 中
 * 仍然保留了泛型签名信息（Signature 属性）。
 *
 * 能保留泛型信息的场景：
 *   1. 类继承/实现时指定了具体类型参数  → 通过 getGenericSuperclass()
 *   2. 字段声明时的泛型类型              → 通过 Field.getGenericType()
 *   3. 方法参数/返回值的泛型类型         → 通过 Method.getGenericParameterTypes()
 *
 * 不能保留泛型信息的场景：
 *   局部变量的泛型信息（如 List<String> list = new ArrayList<>()）
 *   在运行时完全被擦除，无法通过反射获取。
 *
 * 为什么这样设计？
 *   局部变量的泛型信息只在编译期用于类型检查，运行时不需要。
 *   而类的字段、方法签名、父类泛型参数属于类的结构性元数据，
 *   需要保留以支持反射、序列化等框架的正确工作。
 */

import java.lang.reflect.*;

// ---- 场景 1: 通过继承保留泛型信息 ----

public abstract class BaseDao<T> {
    private Class<T> entityClass;

    @SuppressWarnings("unchecked")
    public BaseDao() {
        // 获取带泛型参数的父类类型
        Type genericSuperclass = getClass().getGenericSuperclass();

        if (genericSuperclass instanceof ParameterizedType) {
            ParameterizedType paramType = (ParameterizedType) genericSuperclass;
            // getActualTypeArguments() 返回实际类型参数数组
            Type[] typeArgs = paramType.getActualTypeArguments();
            entityClass = (Class<T>) typeArgs[0];
        }
    }

    public Class<T> getEntityClass() {
        return entityClass;
    }
}

// 子类继承时指定了具体类型 → 泛型信息被写入字节码的 Signature 属性
public class UserDao extends BaseDao<User> {
    // entityClass 会被正确解析为 User.class
}


// ---- 场景 2: 通过字段反射获取泛型信息 ----

public class Repository {
    private List<String> names;
    private Map<String, List<Integer>> dataMap;
}
```

### 3.3 Retrofit 中的泛型解析原理

```java
/**
 * Retrofit 的核心设计：通过 动态代理 + 反射 解析接口方法的泛型返回值，
 * 从而知道如何反序列化服务器响应。
 *
 * 为什么 Retrofit 能拿到泛型信息？
 * 因为接口方法的返回值类型属于 **方法签名的元数据**，
 * 这些信息在编译后保存在字节码的 Signature 属性中，可通过反射获取。
 */

// ---- 第一步: 用户定义接口 ----
public interface ApiService {
    @GET("users/{id}")
    Call<User> getUser(@Path("id") int id);

    @GET("users")
    Call<List<User>> getUsers();
}


// ---- 第二步: Retrofit.create() 核心实现 (简化版) ----

public <T> T create(final Class<T> service) {
    // 动态代理: 拦截接口方法调用
    return (T) Proxy.newProxyInstance(
        service.getClassLoader(),
        new Class<?>[]{ service },
        new InvocationHandler() {
            @Override
            public Object invoke(Object proxy, Method method, Object[] args)
                    throws Throwable {
                // 解析方法的注解和泛型返回值
                return loadServiceMethod(method).invoke(args);
            }
        }
    );
}


// ---- 第三步: 解析方法返回值的泛型类型 ----

/**
 * Retrofit 内部的 ServiceMethod 会解析 Method 的返回值类型
 * 例如: Call<User> → 提取出 User.class 用于 JSON 反序列化
 */
static Type getParameterUpperBound(int index, ParameterizedType type) {
    Type[] types = type.getActualTypeArguments();
    Type paramType = types[index];
    if (paramType instanceof WildcardType) {
        return ((WildcardType) paramType).getUpperBounds()[0];
    }
    return paramType;
}

/**
 * Retrofit 的 Utils.getCallResponseType() 简化逻辑:
 */
static Type getCallResponseType(Type returnType) {
    // returnType = Call<User>
    if (!(returnType instanceof ParameterizedType)) {
        throw new IllegalArgumentException(
            "Call return type must be parameterized as Call<Foo>");
    }
    // 提取 Call<User> 中的 User
    return getParameterUpperBound(0, (ParameterizedType) returnType);
}
```

### 3.4 Gson 反序列化泛型原理（TypeToken）

```java
/**
 * Gson 反序列化泛型时的核心问题：
 *
 *   Gson gson = new Gson();
 *   // ❌ 错误: 类型擦除后 Gson 不知道 List 里装的是什么
 *   List<User> users = gson.fromJson(json, List.class);
 *   // 结果: List 里的元素是 LinkedTreeMap，不是 User
 *
 * 解决方案: 使用 TypeToken 通过匿名子类保留泛型信息
 */

// ---- TypeToken 的正确用法 ----

Gson gson = new Gson();
String json = "[{\"name\":\"Alice\"},{\"name\":\"Bob\"}]";

// ✓ 正确: 使用 TypeToken 创建匿名子类
Type type = new TypeToken<List<User>>(){}.getType();
List<User> users = gson.fromJson(json, type);
// 结果: List 里的元素是 User 对象


// ---- TypeToken 源码原理 (简化版) ----

/**
 * TypeToken 的核心原理：
 * new TypeToken<List<User>>(){} 创建了一个 **匿名子类**。
 * 匿名子类继承 TypeToken 时指定了具体类型参数 List<User>，
 * 这个信息被写入了字节码的 Signature 属性。
 * 构造函数中通过 getClass().getGenericSuperclass() 就能拿到。
 *
 * 这和前面 BaseDao<User> 的原理完全一样：
 * 通过子类继承父类时指定的具体类型参数，绕过类型擦除。
 */
public class TypeToken<T> {
    final Type type;

    protected TypeToken() {
        // this.getClass() 返回的是匿名子类的 Class
        // getGenericSuperclass() 返回 TypeToken<List<User>>
        Type superclass = getClass().getGenericSuperclass();
        if (superclass instanceof ParameterizedType) {
            // 提取 List<User> 这个完整的泛型类型
            this.type = ((ParameterizedType) superclass)
                            .getActualTypeArguments()[0];
        } else {
            throw new RuntimeException("Missing type parameter.");
        }
    }

    public Type getType() {
        return type;
    }
}
```

```kotlin
/**
 * 使用泛型封装 BaseActivity，自动处理 ViewBinding 的创建和销毁。
 *
 * 为什么这样设计？
 *   - 每个 Activity 都需要 inflate ViewBinding，代码完全重复
 *   - 泛型 + 反射可以将这部分样板代码提取到基类
 *   - 子类只需声明泛型参数，无需手动 inflate
 *
 * 依据：ViewBinding 的 inflate 方法签名是固定的 (inflate(LayoutInflater))，
 * 可以通过反射统一调用。
 */
abstract class BaseActivity<VB : ViewBinding> : AppCompatActivity() {

    private var _binding: VB? = null
    protected val binding: VB get() = _binding!!

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        _binding = inflateBinding()
        setContentView(binding.root)
        initView()
    }

    @Suppress("UNCHECKED_CAST")
    private fun inflateBinding(): VB {
        // 通过反射获取泛型参数的实际类型
        val type = javaClass.genericSuperclass as ParameterizedType
        val clazz = type.actualTypeArguments[0] as Class<VB>
        val method = clazz.getMethod("inflate", LayoutInflater::class.java)
        return method.invoke(null, layoutInflater) as VB
    }

    abstract fun initView()

    override fun onDestroy() {
        super.onDestroy()
        _binding = null  // 防止内存泄漏
    }
}

// 使用：子类只需声明泛型参数
class UserActivity : BaseActivity<ActivityUserBinding>() {
    override fun initView() {
        binding.tvName.text = "Hello"
    }
}
```

#### 4.1.3 泛型 RecyclerView Adapter

```kotlin
/**
 * 通用的 RecyclerView Adapter 泛型封装。
 *
 * 为什么这样设计？
 *   - RecyclerView.Adapter 的样板代码非常多
 *   - 使用泛型 <T, VB> 可以让一个基类适配所有数据类型和布局
 *   - DiffUtil 的接入也可以在基类统一处理
 *
 * 实际项目中的价值：
 *   减少 70% 以上的 Adapter 样板代码，新增列表页只需关注绑定逻辑。
 */
abstract class BaseAdapter<T, VB : ViewBinding>(
    private val inflate: (LayoutInflater, ViewGroup, Boolean) -> VB
) : ListAdapter<T, BaseAdapter<T, VB>.ViewHolder>(DiffCallback()) {

    inner class ViewHolder(val binding: VB) : RecyclerView.ViewHolder(binding.root)

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): ViewHolder {
        val binding = inflate(LayoutInflater.from(parent.context), parent, false)
        return ViewHolder(binding)
    }

    override fun onBindViewHolder(holder: ViewHolder, position: Int) {
        bind(holder.binding, getItem(position), position)
    }

    abstract fun bind(binding: VB, item: T, position: Int)

    // DiffUtil 回调 (简化版，实际项目中应由子类提供比较逻辑)
    class DiffCallback<T> : DiffUtil.ItemCallback<T>() {
        override fun areItemsTheSame(oldItem: T & Any, newItem: T & Any) =
            oldItem === newItem
        override fun areContentsTheSame(oldItem: T & Any, newItem: T & Any) =
            oldItem == newItem
    }
}

// 使用

        binding.tvName.text = item.name
        binding.tvEmail.text = item.email
```

#### 4.2.1 Retrofit：动态代理 + 反射

```java
/**
 * Retrofit 是反射在 Android 中最经典的应用之一。
 *
 * 工作原理:
 *   1. 动态代理 (Proxy.newProxyInstance) 拦截接口方法调用
 *   2. 反射解析方法上的注解 (@GET, @POST, @Query 等) 构建 HTTP 请求
 *   3. 反射解析方法返回值的泛型类型 (如 Call<User>) 确定反序列化目标
 *
 * 为什么 Retrofit 选择反射而不是 APT？
 *   - 接口方法的调用是运行时行为，需要动态拦截
 *   - 动态代理只能在运行时工作，必须配合反射
 *   - 性能优化: 解析结果被缓存在 ConcurrentHashMap 中，每个方法只解析一次
 */

// Retrofit 内部 ServiceMethod 缓存机制 (简化版)
private final Map<Method, ServiceMethod<?>> serviceMethodCache = new ConcurrentHashMap<>();

ServiceMethod<?> loadServiceMethod(Method method) {
    // 先查缓存
    ServiceMethod<?> result = serviceMethodCache.get(method);
    if (result != null) return result;

    synchronized (serviceMethodCache) {
        result = serviceMethodCache.get(method);
        if (result == null) {
            // 解析方法注解和泛型，构建 ServiceMethod
            result = ServiceMethod.parseAnnotations(this, method);
            serviceMethodCache.put(method, result);
        }
    }
    return result;
}
```

## 5. 常见面试题

### 问题1：什么是类型擦除？有什么影响？

**答案要点**：
- **定义**：Java 泛型是"伪泛型"，泛型信息只在编译期存在，编译后会被擦除。无界类型参数 `<T>` 被替换为 `Object`，有界类型参数 `<T extends Comparable>` 被替换为第一个边界 `Comparable`
- **设计原因**：为了向后兼容 JDK 5 之前的非泛型代码。如果引入"真泛型"（如 C# 的具化泛型），旧代码无法在新 JVM 上运行
- **影响**：
  1. 不能使用基本类型作为类型参数（`List<int>` ❌，必须用 `List<Integer>`）
  2. 不能创建泛型实例（`new T()` ❌）和泛型数组（`new T[10]` ❌）
  3. 不能用 `instanceof` 检查泛型类型（`obj instanceof List<String>` ❌）
  4. 静态成员不能使用类的泛型参数
  5. 运行时无法直接区分 `List<String>` 和 `List<Integer>`
- **绕过方式**：通过子类继承指定泛型参数（TypeToken 模式）、传递 `Class<T>` 参数、Kotlin 的 `reified` 关键字

### 问题2：List\<String> 和 List\<Integer> 在运行时的区别？

**答案要点**：
- **运行时没有区别**。由于类型擦除，两者在运行时都是 `List`（原始类型），`getClass()` 返回的都是 `java.util.ArrayList`
- 验证方式：`new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()` 结果为 `true`
- 甚至可以通过反射绕过泛型限制，向 `List<String>` 中添加 `Integer`：
  ```java
  List<String> list = new ArrayList<>();
  list.getClass().getMethod("add", Object.class).invoke(list, 123);
  // 不会报错，因为运行时 list 的实际类型就是 ArrayList<Object>
  ```
- **但编译期有区别**：编译器会阻止类型不匹配的操作（如向 `List<String>` 中 add 一个 `Integer`），并自动插入 `checkcast` 指令保证类型安全
- **面试延伸**：这就是为什么 Java 的泛型被称为"语法糖"——类型安全检查完全在编译期完成

### 问题3：为什么 Kotlin 有 reified 关键字？

**答案要点**：
- **问题背景**：由于类型擦除，泛型函数中无法获取 `T` 的实际类型（不能写 `T::class`）
- **reified 的作用**：让泛型参数在运行时可获取（"具化"）
- **实现原理**：`reified` 必须配合 `inline` 使用。`inline` 函数在编译时会被内联展开到调用处，编译器将泛型参数 `T` 替换为调用处的实际类型。所以不是真的保留了泛型信息，而是消除了泛型
  ```kotlin
  // 定义
  inline fun <reified T> isType(value: Any): Boolean = value is T

  // 调用处
  isType<String>("hello")

  // 编译后（内联展开）等价于:
  "hello" is String  // T 被替换为 String
  ```
- **典型使用场景**：
  1. `startActivity<TargetActivity>()` —— 避免传 `Class` 参数
  2. `Gson.fromJson<User>(json)` —— 自动推断反序列化类型
  3. `intent.getParcelableExtra<User>("key")` —— 类型安全的 Extra 获取
- **限制**：只能用于 `inline` 函数，不能用于类的泛型参数，Java 无法调用

### 问题4：Gson 的 TypeToken 是怎么保留泛型信息的？

**答案要点**：
- **核心原理**：利用 JVM 会在字节码的 Signature 属性中保留「类继承/实现时指定的具体泛型参数」这一特性
- **具体机制**：
  1. `new TypeToken<List<User>>(){}` 创建了一个匿名内部类
  2. 该匿名类继承了 `TypeToken<List<User>>`，具体类型 `List<User>` 被写入字节码
  3. TypeToken 构造函数中调用 `getClass().getGenericSuperclass()` 获取到 `ParameterizedType`
  4. 再通过 `getActualTypeArguments()` 提取出 `List<User>` 这个完整类型
- **注意 `{}` 不能省略**：`new TypeToken<List<User>>()` 不创建匿名子类，泛型信息会被擦除；加了 `{}` 才会创建匿名子类
- **同类技巧**：Retrofit、Jackson、Guava 等框架都使用了相同的原理来获取泛型信息

### 问题5：PECS 原则是什么？

**答案要点**：
- **PECS = Producer Extends, Consumer Super**（生产者用 extends，消费者用 super）
- **`<? extends T>`（上界通配符）**：只能读取，不能写入。适用于生产者场景——你从集合中**取出**数据
  - 为什么不能写入？编译器不知道集合的具体类型，如果是 `List<Integer>` 你写入 `Double` 就出错了
  - 可以安全读取为 `T` 类型（一定是 T 的子类，向上转型安全）
- **`<? super T>`（下界通配符）**：可以写入 T 及其子类，读取只能是 Object。适用于消费者场景——你向集合中**放入**数据
  - 为什么能写入？集合至少能容纳 `T`（可能是 `T` 的父类容器）
  - 为什么读取只能是 Object？不知道具体类型，只能退化为 Object
- **Kotlin 中的对应**：`out` 对应 `extends`（协变），`in` 对应 `super`（逆变）
- **实际案例**：`Collections.copy(List<? super T> dest, List<? extends T> src)` —— src 是生产者用 extends，dest 是消费者用 super

### 问题6：反射的性能影响和优化方式

**答案要点**：
- **性能影响来源**：
  1. **方法查找开销**：`getDeclaredMethod()` 需要遍历类的方法表，O(n) 复杂度
  2. **安全检查**：每次 `invoke()` 都要做访问权限检查
  3. **JIT 优化受阻**：反射调用是动态分派，JIT 编译器无法内联优化
  4. **自动装箱**：反射调用参数必须是 `Object[]`，基本类型需要装箱
- **优化方式**：
  1. **缓存 Method/Field 对象**：只做一次查找，后续复用（Retrofit 就是这样做的）
  2. **setAccessible(true)**：跳过安全检查，可提速 4-7 倍
  3. **用 APT 替代反射**：将运行时反射逻辑移到编译期代码生成（Dagger 2 的做法）
  4. **MethodHandle (Java 7+)**：比反射更快，更接近直接调用的性能
  5. **使用 Kotlin 委托/扩展代替**：很多反射场景可以用语言特性替代
- **实际数据**：反射调用比直接调用慢 5-50 倍（取决于是否缓存），但在大多数非热点路径上影响可忽略。核心原则是**避免在循环和高频调用路径上使用未缓存的反射**

### 问题7：Retrofit 是如何通过反射和动态代理实现接口调用的？

**答案要点**：
- **整体流程**：
  1. `Retrofit.create(ApiService.class)` 使用 `Proxy.newProxyInstance()` 为接口创建动态代理对象
  2. 调用接口方法时，`InvocationHandler.invoke()` 被触发
  3. 通过反射获取 `Method` 对象上的注解（`@GET`、`@POST`、`@Query` 等）和泛型返回值类型
  4. 根据注解信息构建 `okhttp3.Request` 对象
  5. 根据返回值泛型类型（如 `Call<User>` 中的 `User`）选择合适的 `Converter` 进行反序列化
- **性能优化**：
  - 每个 `Method` 只解析一次，结果缓存在 `ConcurrentHashMap<Method, ServiceMethod>` 中
  - 后续调用同一方法直接从缓存获取，不再反射
- **为什么用动态代理而不是 APT？**
  - 接口方法调用是运行时行为，APT 在编译期无法拦截方法调用
  - 动态代理让用户只需定义接口，无需写实现类，使用体验极佳
- **Kotlin 协程支持**：Retrofit 2.6+ 检测到方法是 `suspend` 函数时，会特殊处理 `Continuation` 参数

### 问题8：APT 和反射的区别，各自适用场景

**答案要点**：

| 维度 | APT（注解处理器） | 反射 |
|------|-------------------|------|
| **执行时机** | 编译期（javac 阶段） | 运行时 |
| **性能影响** | 增加编译时间，运行时零开销 | 编译无影响，运行时有开销 |
| **错误发现** | 编译期报错 | 运行时才暴露 |
| **灵活性** | 只能处理编译期已知的信息 | 可以处理运行时动态信息 |
| **产物** | 生成新的 Java/Kotlin 源文件 | 无产物，直接操作对象 |
| **混淆影响** | 生成的代码随混淆自动适配 | 需要手动 keep 规则 |

- **APT 适用场景**：依赖关系在编译期确定的场景
  - 依赖注入：Dagger/Hilt（编译期构建依赖图）
  - 视图绑定：ButterKnife（编译期知道所有 View ID）
  - 数据库 ORM：Room（编译期知道 SQL 和实体类结构）
  - 路由表：ARouter（编译期收集所有路由注册）
- **反射适用场景**：需要运行时动态性的场景
  - 动态代理：Retrofit（运行时拦截接口调用）
  - 框架内部：Spring（运行时扫描和注入 Bean）
  - 热修复/插件化：动态加载和替换类
  - 序列化/反序列化：Gson（运行时创建任意类型的实例）
- **最佳实践**：能用 APT 就不用反射。如果必须用反射，一定要缓存 `Method`/`Field` 对象，并配置好 ProGuard keep 规则
