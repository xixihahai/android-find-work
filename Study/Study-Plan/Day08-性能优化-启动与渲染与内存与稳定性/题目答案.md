## 口述题

#### 1. 冷启动的完整链路，每个环节可以做什么优化？（口述题）
**要点：**
- Launcher → Zygote fork → Application.attach → ContentProvider → Application.onCreate → Activity.onCreate/onStart/onResume → 首帧绘制。
- 优化点：预加载、延迟初始化、SplashScreen API、异步任务调度、布局优化。

**解析：**
冷启动从点击图标开始，Zygote fork 新进程后会执行 `ActivityThread.main`，按顺序创建 Application、初始化 ContentProvider、调用 Application#onCreate，再到 Activity 生命周期和 View 绘制。优化可分为：减少主线程阻塞（避免在 Application.onCreate 做 I/O）、通过 `AppStartup`/`InitProvider` 管理初始化顺序、使用 `SplashScreen` 保持首帧一致、LayoutInspector/ConstraintLayout 降低层级、延迟网络请求到首屏之后。

#### 2. LeakCanary 是如何检测 Activity 泄漏的？（口述题）
**要点：**
- 通过 `ActivityLifecycleCallbacks` 监听 destroy，向引用队列中放置弱引用；
- 等待 GC，若对象仍未从弱引用中回收，则触发 Heap Dump；
- 使用 Shark 解析 Heap Dump，定位 GC Roots 到泄漏对象的最短路径。

**解析：**
LeakCanary 在 Activity 销毁后把对象包裹成 `KeyedWeakReference` 放进 `ReferenceQueue` 并触发一次 GC。若一段时间后引用仍未入队，说明还有强引用链存在，就执行 `Debug.dumpHprofData`，Shark 用图算法分析并给出泄漏链（如静态单例持有 Context、Handler 未移除）。

#### 3. 收到一个 ANR 的 traces.txt，你会看哪些信息来定位问题？（口述题）
**要点：**
- 定位主线程堆栈：看是否卡在 I/O、锁等待、死循环。
- 查看 `"main"` 线程之前的 `Cmd line`、`"Binder:..."` 等线程状态，确认是 Input/Service/Broadcast ANR。
- 结合 `Cpu usage`、`process stats` 分析是否系统压力导致。

**解析：**
traces 文件中 `----- pid ...` 表示进程 snapshot。优先检查 main 线程：若卡在 `synchronized`/`wait`, 关注持锁线程；若在 `ContentProvider`/I/O，说明需下放到子线程。`Input dispatching timed out`/`Broadcast of Intent` 等关键字表明触发类型。配合 `logcat` 中的 `ActivityManager` 日志可确定触发时间和组件名称。

## 场景分析题

#### 4. 线上用户反馈 App 启动慢（冷启动 3s），你的排查和优化思路？列出至少 5 个优化手段（场景分析题）
**要点：**
- 采集启动埋点：`Process.start` → `Activity.reportFullyDrawn`，区分冷/热启动。
- 检查 Application/ContentProvider 阶段是否执行耗时初始化；可按需懒加载。
- 优化布局：ConstraintLayout、ViewStub、移除嵌套。
- 使用 `StartUp`/`InitProvider` 管理依赖，尽量在后台线程初始化。
- 预加载资源但避免同步 I/O（使用 `Resources.preload`、`AssetManager`）。

**解析：**
具体手段：1) 启动链路打点 + `Systrace`；2) 关闭不必要的 ContentProvider（如 `MultiDex`、`WorkManager` 可延迟）；3) 使用 `SplashScreen` + 预绘制 skeleton；4) 缩小 Dex/资源；5) 使用并行初始化（`FutureTask`/`CompletableFuture`）。

#### 5. Memory Profiler 显示内存锯齿状波动（频繁 GC），如何定位是哪里在分配大量临时对象？（场景分析题）
**要点：**
- 使用 Allocation Tracker/`record allocations` 捕获热点方法。
- 打开 `System Trace` 看每帧分配情况，结合 `dumpsys meminfo`。
- 重点排查 Adapter.onBind、Bitmap decode、字符串拼接等高频路径。

**解析：**
Memory Profiler 可实时显示分配栈，捕获 5~10s 内的 `alloc stack`. 通过 diff 分析找到突增对象类型，再回到代码中合并对象、复用 Buffer。必要时使用 `Android Studio Allocation Sampled` 或引入 `LeakCanary` Heap Dump 分析。

## 代码题

#### 6. 写一个简单的启动耗时监控器（统计 Application.onCreate 到首帧渲染完成的时间）（代码题）
**要点：**
- 在 `Application#onCreate` 记录起始时间。
- 在首个 Activity `onWindowFocusChanged` 或 `reportFullyDrawn` 中计算耗时。
- 上报结果并可写入日志。

**解析：**
示例中通过 `ProcessLifecycleOwner` 监听首个 `ON_START`，也可基于 `Choreographer` 回调记首帧。

**示例代码：**
```kotlin
class PerfApp : Application(), Application.ActivityLifecycleCallbacks {
    private var startNs: Long = 0L
    private var reported = false

    override fun onCreate() {
        super.onCreate()
        registerActivityLifecycleCallbacks(this)
        startNs = System.nanoTime()
    }

    override fun onActivityResumed(activity: Activity) {
        if (!reported) {
            activity.window.decorView.viewTreeObserver.addOnDrawListener(object : ViewTreeObserver.OnDrawListener {
                override fun onDraw() {
                    if (reported) return
                    reported = true
                    val costMs = (System.nanoTime() - startNs) / 1_000_000
                    Log.d("StartupMonitor", "Cold start cost: ${costMs}ms")
                    activity.window.decorView.viewTreeObserver.removeOnDrawListener(this)
                }
            })
        }
    }

    // 其余生命周期方法可留空
    override fun onActivityCreated(a: Activity, b: Bundle?) {}
    override fun onActivityStarted(a: Activity) {}
    override fun onActivityPaused(a: Activity) {}
    override fun onActivityStopped(a: Activity) {}
    override fun onActivitySaveInstanceState(a: Activity, outState: Bundle) {}
    override fun onActivityDestroyed(a: Activity) {}
}
```

**说明：**
`OnDrawListener` 可在首帧绘制后立即回调。真实项目可上报到监控平台，并区分冷/热启动（如通过 `ActivityManager.getRunningTasks` 或自定义标记）。
